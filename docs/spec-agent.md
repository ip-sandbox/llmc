# AI 側の制御仕様（規則の注入と専用エージェント）

> **状態: 暫定版**。実物で確かめる仮説は plan.md 5.2 にまとめた。PoC の結果を受けて確定・修正する。

## 1. 2 つの方式

| 方式 | 名前 | 内容 | 必須か |
|---|---|---|---|
| 基本 | `prompt-rules` | 通常のチャット画面に、書式の規則をプロンプトに入れて送る | **必須**。これだけで UC1〜UC3、UC5 のすべてが動く |
| オプション | `agent` | M365 Copilot のエージェントビルダーで作った llmc 専用のエージェントを使い、指示文で規則を固定する。プロンプトの規則は短くする | 任意。使えなくても機能は欠けない |

- 設定でエージェントを指定しなければ `prompt-rules` で動く。エージェントを使うための設定は一切必須にしない
- エージェントビルダーが組織で使えるか、指示文の文字数の上限、エージェントの画面の DOM は、調べてから確定する（open-questions）

## 2. 規則の原本

### 2.1 構成

規則の原本は llmc のリポジトリに 1 つだけ置き、プロンプト用とエージェントの指示文用の両方をそこから生成する。

```
src/llmc/protocol/rules/v1/
  rules.yaml       規則の本文（節ごと）
  examples/        例（書式の回答の例など）
```

`rules.yaml` の節（例）:

| 節 | 内容 | 長い版 | 短い版 |
|---|---|---|---|
| `role` | llmc が仲介していること、AI 自身はファイルを書けず、コマンドも実行できないこと、実行結果は llmc が返すこと | ○ | ○ |
| `plan` | 回答の最初に、出力する項目の一覧（計画）を書くこと | ○ | ○ |
| `file_block` | ファイルの書き出しの書式（全文、省略しない、内側の開始行と終了行、`base`、フェンス 4 個以上、**フェンスに言語名を書かない**） | ○ | ○（1〜2 行） |
| `delete` | 削除の書式（`LLMC-DELETE` の 1 行だけ。**`LLMC-FILE` で囲まない**） | ○ | ○（1 文） |
| `read` | 読み取り要求の書式と、読み取りと書き込みを同じ回答に混ぜないこと | ○ | — |
| `done` | 回答の最後に終了行を書くこと、版と ID の書き返し | ○ | ○ |
| `continuation` | 続きの依頼のときは、指定された項目をすべて出すこと | ○ | — |
| `style` | 前置きや謝罪を書かない、変更点は 3 行以内、推測した実行結果を書かない | ○ | ○ |
| `no_tools` | ファイルをツール（コードインタープリターなど）で作らず、テキストで出力すること | ○（ループ用） | ○（ループ用） |
| `binary` | バイナリを作る依頼のときの扱い（spec-convert） | ○（変換用） | — |

各節には、どの用途（`chat`、`loop`、`convert`）で使うかを付ける。

### 2.2 規則の版（`rev`）

- `rev` は、`rules.yaml` と `examples/` の内容（正規化したもの）の SHA-256 の先頭 6 文字
- AI は `LLMC-DONE` に `rev` を書く（spec-file-protocol 13 章）。**`rev` の出どころは方式によって違う**

| 方式 | プロンプトに `rev` を書くか | AI が書く `rev` の出どころ | llmc が比べる相手 | 分かること |
|---|---|---|---|---|
| `prompt-rules` | 書く | プロンプト | 送った `rev` | AI がプロンプトの規則を読んだか（補助的な確認） |
| `agent` | **書かない** | エージェントの指示文に埋め込んだ値 | 利用者の設定に記録した、反映済みの `rev`（6 章）と、現在の規則の `rev` | 指示文が古い（現在の規則と違う）、または画面への反映を忘れた |

- `agent` 方式でプロンプトに `rev` を書くと、AI はそれを写すだけになり、指示文が古くても気付けない。そのため `agent` 方式ではプロンプトに `rev` を書かない
- `agent` 方式で回答の `rev` が現在の規則と違う場合は `W_REV_MISMATCH`（「指示文が古い。`llmc agent build` で作り直し、画面に反映してください」）。`rev` が無い場合は、エージェントではなく通常のチャットで動いている恐れもあるので、警告に添える

### 2.3 生成

| 生成物 | 生成元 | 生成する操作 |
|---|---|---|
| プロンプト用の規則（長い版） | 用途に合う節の長い版 | 送信のたびに llmc が生成 |
| プロンプト用の規則（短い版） | 用途に合う節の短い版 | 同上 |
| エージェントの指示文 | 用途に合う節の長い版＋エージェント用の前文 | `llmc agent build <名前>` |

## 3. 指示文とプロンプトの分担

| 内容 | `prompt-rules` のプロンプト | `agent` の指示文 | `agent` のプロンプト |
|---|---|---|---|
| 役割（仲介者がいる、実行できない） | 長い版 | ○ | — |
| ファイルの書式 | 長い版 | ○ | 短い版（1〜2 行の念押し） |
| 読み取り要求、削除、続きの依頼 | 長い版（用途で必要なものだけ） | ○ | — |
| 終了行 | 長い版 | ○ | 短い版 |
| 文体（前置き無し） | 長い版 | ○ | — |
| プロトコルの版 | ○ | ○ | ○ |
| 規則の版（`rev`） | ○ | ○（生成時の値を埋め込む） | **書かない**（2.2） |
| ターン ID | ○ | — | ○ |
| 書き込みを許可するパス、変更禁止のパス | ○ | — | ○ |
| タスク・目的・制約・文脈・履歴 | ○ | — | ○ |
| そのターンの上限（ファイル数など） | ○ | — | ○ |

### 3.1 会話の途中での扱い

| 状況 | `prompt-rules` | `agent` |
|---|---|---|
| 会話の最初のターン | 長い版 | 短い版 |
| 同じ会話の 2 ターン目以降 | 短い版 | 短い版 |
| 直前のターンが形式違反 | 長い版（違反の内容を添える） | 長い版（違反の内容を添える） |
| 一定のターン数ごと（既定 5） | 長い版 | 短い版 |

`agent` でも短い版の念押しを残す。指示文だけに頼ると、会話が長くなったときに書式が崩れる恐れがあるため。

### 3.2 長さの目安

| 生成物 | 目安 |
|---|---|
| 長い版（ループ用） | 2,000 文字以内 |
| 短い版 | 300 文字以内 |
| エージェントの指示文 | エージェントビルダーの上限の 7 割以内（上限は調査項目。分かるまでは 4,000 文字を目標にする） |

## 4. 知識ファイルを使うか

| 案 | 利点 | 欠点 |
|---|---|---|
| 指示文だけ | 毎回必ず効く | 指示文の上限に収める必要がある |
| 知識ファイルに書式の仕様を置く | 長い仕様や例を置ける | 知識ファイルは検索して参照されるので、**毎回必ず読まれる保証が無い** |

**判断**: 書式の規則は**指示文だけ**に入れる。知識ファイルは使わないことを基本とし、長い例（入れ子のフェンスの例など）が必要になった場合に限り、補助として置く。知識ファイルを置いても、規則の本体は指示文に残す。

## 5. エージェントの構成

### 5.1 用途ごとのエージェント

| 名前（例） | 用途 | コードインタープリター | Web 検索 | 知識ファイル |
|---|---|---|---|---|
| `llmc-loop` | UC3（UC4） | **無効** | 無効 | 無し |
| `llmc-convert` | UC5 | 有効（方式 B に必要な場合） | 無効 | 無し |
| `llmc-chat` | UC1、UC2 | 任意 | 任意 | 任意 |

- UC3 でコードインタープリターを有効にすると、AI が自分の側でファイルを作ってしまい、テキストで出力されない恐れがある。そのため用途ごとにエージェントを分け、ループ用では無効にする
- 通常のチャット画面（エージェント無し）でコードインタープリターに相当する機能が使えるか、無効にできるかは調査項目とする。使えてしまう場合は、`no_tools` の節でテキストでの出力を求め、ファイルの成果物が返ってきたら形式違反として扱う（`E_TOOL_ARTIFACT`。ループでのみ）

### 5.2 指示文の案（`llmc-loop`、骨子）

```text
# 役割
あなたは llmc というツールを介して利用者とやり取りします。llmc があなたの回答からファイルを取り出して保存し、利用者が決めたコマンドで実行して、その結果を次の依頼として返します。あなた自身はファイルを保存できず、コマンドも実行できません。実行結果を推測して書かないでください。

# 回答の書式（llmc/1）
- 回答の最初のコードブロックに、出力する項目を1行ずつ書く: LLMC-PLAN id=<依頼のID> write="<相対パス>"（削除は delete=、読み取りは read=）
- ファイルを出すときは、ファイル全体を省略せずに、バッククォート4個以上のコードブロックに入れる。フェンスの開きの行には言語名を書かない。
  ブロックの1行目に LLMC-FILE id=<依頼のID> path="<相対パス>" base=<送られたsha、新規なら new>、
  最終行に LLMC-END id=<依頼のID> path="<相対パス>" を書く。
- 削除は、コードブロックの中に LLMC-DELETE id=<依頼のID> path="<相対パス>" の1行だけを書く。LLMC-FILE で囲まない。
- （読み取り要求、続きの依頼の規則）
- 回答の最後に、コードブロックの中に LLMC-DONE v=1 id=<依頼のID> rev=3fa9c1 を書く。
  rev の値は、この指示文に書かれた 3fa9c1 をそのまま使う（依頼文には書かれない）。
- ファイルをツールで作成しない。必ずテキストで出力する。

# 文体
前置き・謝罪・繰り返しを書かない。変更点は3行以内。

（rev: 3fa9c1 / 生成日時 / 生成元: llmc <版>）
```

本文は `rules.yaml` から生成するので、上は形の例である。`3fa9c1` の部分は生成時の `rev` に置き換わる。

## 6. 指示文の管理と画面への反映

出力先は `llmc agent build <名前> -o <ディレクトリ>` で指定する。指定しなければ `%LOCALAPPDATA%\llmc\agents\` に出す（venv に入れた llmc にはリポジトリが無いため）。変更履歴を残すために、利用者が管理するリポジトリ（llmc の開発リポジトリ、または設定を管理する個人のリポジトリ）を出力先にすることを推奨する。

```
<出力先>/
  llmc-loop/
    agent.yaml            名前、用途、有効にする機能、知識ファイル、対象の rev
    instructions.md       生成した指示文（コミットして変更履歴を残す）
    CHANGELOG.md          変更の理由
  llmc-convert/ ...
```

| 手順 | 操作 |
|---|---|
| 1. 生成 | `llmc agent build llmc-loop -o <出力先>` が `instructions.md` を作り直す。前回との差分を表示する |
| 2. 記録 | 利用者が `instructions.md` と `CHANGELOG.md` をコミットする |
| 3. 反映 | 利用者がエージェントビルダーの画面に貼り付ける（**手作業**。llmc は画面を自動操作しない） |
| 4. 登録 | `llmc agent mark-applied llmc-loop` で、反映した `rev` を利用者の設定に記録する |
| 5. 確認 | `llmc probe --agent llmc-loop` で、回答に書かれた `rev`（指示文から来たもの）が、記録した `rev` と現在の規則の `rev` の両方に一致することを確かめる |

- llmc は、利用者の設定に記録した `rev` と、現在の規則の `rev` が違えば、エージェントを使うたびに警告する（「指示文が古い。`llmc agent build` で作り直し、画面に反映してください」）
- エージェントビルダーの画面を自動操作しない理由: 頻度が低い作業で、自動化の利点が小さく、管理画面の操作は社内規程の確認の範囲が広がるため

## 7. エージェントの選び方

### 7.1 設定

```yaml
# %LOCALAPPDATA%\llmc\config.yaml
agents:
  llmc-loop:
    site: copilot-m365
    open: {url: "https://..."}          # エージェントごとの URL がある場合
    # open: {picker: "llmc-loop"}       # 画面上で名前を選ぶ場合
    identify: {text: "llmc-loop"}       # 正しく開けたかの確認（画面に出る名前）
    on_unavailable: fallback            # fallback / error
use:
  loop: llmc-loop                       # 用途ごとの既定。書かなければエージェント無し
  convert: null
  chat: null
```

- コマンドの引数 `--agent <名前>` と `--no-agent` で、その実行だけ切り替えられる
- ループ定義に `agent:` を書いた場合はそれを優先する

### 7.2 ドライバへの影響

- エージェントの画面とチャット画面で DOM が違う可能性がある。サイト別プロファイルの `variants.agent` で、違うセレクタだけを上書きする（spec-browser-driver 3.2）
- `new_conversation(agent)` は、`open` の方法でエージェントの画面を開き、`identify` で確かめてから入力欄を待つ
- 会話の URL がエージェントの画面のものになるので、続行は同じエージェントで行われる

## 8. エージェントを使えなくなった場合

### 8.1 検知

- `open` の URL が開けない、見つからない旨の表示が出る、`identify` の文字が見つからない、`picker` に名前が無い → `AgentUnavailable`

### 8.2 方針

| 時点 | 既定の動作 | 理由 |
|---|---|---|
| 対話・単発（UC1、UC2） | `on_unavailable: fallback`。stderr に警告を出し、`prompt-rules` で続ける。JSON に `agent_fallback: true` を入れる | 規則をプロンプトに入れれば同じ機能が動くので、止める理由が小さい |
| ループの開始時（UC3） | 同上（`fallback`） | 開始前なら、全ラウンドを同じ条件で回せる |
| ループの途中 | **エラーで止める**（終了コードは spec-shell-integration） | 途中で方式が変わると条件が揃わず、形式違反の傾向や結果を比べられなくなる。再開（`llmc loop resume`）時に方式を選び直せる |
| 変換（UC5）で方式 B のためにエージェントが必要な場合 | 方式 C か A に切り替えられるレシピなら切り替え、できなければエラー | spec-convert |

- `on_unavailable: error` を指定すれば、どの場合もエラーで止める
- 切り替えたことは run ディレクトリの記録にも残す

## 9. 方式ごとの形式の守られ方の比較

エージェントあり・なしで、同じ依頼の集まりを送り、次を比べる（test-plan）。

| 指標 | 内容 |
|---|---|
| 形式違反の率 | `complete` にならなかったターンの割合（エラーの種類ごと） |
| 途中切れの率 | `truncated` の割合 |
| 長い会話での崩れ | 10 ターン目以降の形式違反の率 |
| プロンプトの長さ | 1 ターンあたりの平均の送信文字数 |
| `rev` の書き返しの率 | 正しく書き返された割合 |

結果によって、`agent` 方式でのプロンプトの短い版の長さや、長い版を送り直す間隔を調整する。
