# 要件定義

## 0. 前提

| 項目 | 内容 |
|---|---|
| ツール名 | `llmc` |
| 言語 | Python（venv にパッケージを追加できる。管理者権限は無い） |
| 対象 OS | Windows のみ（Linux・macOS はサポートしない） |
| 対象シェル | PowerShell 5.1 と cmd.exe のどちらを主にするかは spec-shell-integration で決める。PowerShell 7 は使えない前提 |
| 通信 | ヘッドレスブラウザ（Playwright）による画面操作のみ。差し替え可能なアダプタの裏に隠す |
| 第一ターゲット | Microsoft 365 Copilot Chat。将来は他のチャットにも対応できる構造にする |
| 利用者 | 本人のみ（チーム配布は考えない） |
| 同時実行 | 直列の順番待ちのみ |

要件 ID の書き方: `FR-<領域>-<番号>`（機能要件）、`NFR-<番号>`（非機能要件）。優先度は **M**（必須）/ **S**（あるべき）/ **C**（あれば良い）。

## 1. 共通の機能要件

| ID | 要件 | 優先度 |
|---|---|---|
| FR-COM-01 | 画面操作の部分は共通インタフェース（`ChatBackend`）の裏に隠し、別のアダプタ（API など）に差し替えられること | M |
| FR-COM-02 | サイトごとのセレクタ・抽出方式・機能差を「サイト別プロファイル」として設定ファイルに外出しすること | M |
| FR-COM-03 | 初回ログインは画面ありのブラウザで手動で行い、以降はヘッドレスで再利用すること。セッション切れを検知して再ログインを促すこと | M |
| FR-COM-04 | `llmc probe` で、セレクタ・送信・回答の特定・完了判定・抽出・ファイル書式の往復を診断し、項目ごとに合否を出せること | M |
| FR-COM-05 | 画面の変更で操作が失敗したとき、どの段階のどのセレクタで失敗したかを、スクリーンショットと DOM の断片を添えて報告すること | M |
| FR-COM-06 | ブラウザを常駐させるデーモンと、軽量なクライアント CLI に分けること。デーモンが動いていなければクライアントが自動で起動すること | M |
| FR-COM-07 | 送信前にマスキング規則を必ず適用すること（全コマンド共通） | M |
| FR-COM-08 | 回答テキストの決まった書式（spec-file-protocol）を解析して、ファイルの書き出し・削除・読み取り要求を扱うこと | M |
| FR-COM-09 | 規則（書式の説明）をプロンプトに入れる方式だけで UC1〜UC3、UC5 のすべてが動くこと。専用エージェントはオプション | M |
| FR-COM-10 | 専用エージェントを指定した場合は、プロンプト側の規則を短縮できること | S |
| FR-COM-11 | 応答の生成中にキャンセル（Ctrl+C）できること。キャンセル時は画面上の停止ボタンを押すこと | S |

## 2. UC1：ターミナルからの対話

| ID | 要件 | 優先度 |
|---|---|---|
| FR-UC1-01 | TUI で対話できること。回答はストリーミング表示（生成中は画面上の描画テキスト、完了後に抽出した Markdown に差し替え） | M |
| FR-UC1-02 | 複数行入力ができること（送信キーと改行キーを分ける） | M |
| FR-UC1-03 | 新しいチャットの作成、既存チャットの続行、会話の切り替えができること | M |
| FR-UC1-04 | ローカルの会話履歴（送受信したテキスト、会話の URL）を保存し、一覧・再表示できること | S |
| FR-UC1-05 | ファイルを添付できること。方式は「本文に埋め込む」と「チャット画面の添付機能」から選べること（後者は対応するサイトのみ） | M |
| FR-UC1-06 | 回答に書式どおりのファイルブロックがあれば、差分を表示し、確認してから書き出せること | S |
| FR-UC1-07 | AI からのファイル読み取り要求は、許可リストに合うものだけを、確認してから返すこと | S |
| FR-UC1-08 | AI が提案したコマンドは、ユーザーが確認した後にだけ実行できること（既定は実行しない） | C |

## 3. UC2：シェルとの統合（単発）

| ID | 要件 | 優先度 |
|---|---|---|
| FR-UC2-01 | パイプ入力を受け付けること（`git diff \| llmc ask "レビューして"`）。引数のプロンプトと stdin の内容を区別して送ること | M |
| FR-UC2-02 | 非対話の 1 回実行モードは、入力待ちを一切しないこと。確認が必要な操作に当たった場合は、専用の終了コードで止めること | M |
| FR-UC2-03 | 回答本文だけを stdout に出し、進捗・ログ・警告は stderr に出すこと | M |
| FR-UC2-04 | 結果を JSON（1 オブジェクト）で出せること。JSON には終了コード、状態、回答、会話の URL、警告を含めること | M |
| FR-UC2-05 | 終了コードを用途別に体系化し、JSON の状態と 1 対 1 に対応させること（spec-shell-integration） | M |
| FR-UC2-06 | stdin・stdout の文字コードを指定でき、既定で日本語が文字化けしないこと | M |
| FR-UC2-07 | タスクスケジューラなど、コンソールの無い環境から起動しても動くこと | M |
| FR-UC2-08 | 回答から抽出したコードブロックだけを出力するオプションがあること（例: `--extract code`） | C |

## 4. UC3：ファイル出力と実行結果フィードバックのループ（最重要）

| ID | 要件 | 優先度 |
|---|---|---|
| FR-UC3-01 | ループの設定をループ定義ファイル（YAML）にまとめ、同じ条件で再実行できること | M |
| FR-UC3-02 | ループ定義に次を書けること: タスク・目的・制約 / 毎回送る文脈ファイル / 書き込みを許可するパス / 読み取りを許可するパス / 変更禁止のパス / 実行コマンド・作業ディレクトリ・タイムアウト・環境変数 / 成功条件（終了コード、出力の正規表現、指標の閾値） / 指標の取り出し方と最適化の向き / 終了条件 / チャットに戻すログの量（先頭と末尾の行数） / マスキング規則 / ラウンドごとに新しいチャットにするか | M |
| FR-UC3-03 | AI の回答からファイルを取り出し、許可された場所にだけ書き出すこと。パスは正規化してから判定すること | M |
| FR-UC3-04 | ユーザーがループ定義に書いたコマンドだけを実行すること。AI にコマンドを決めさせないこと | M |
| FR-UC3-05 | 終了コード、stdout・stderr、出力ファイル、指標を集めること | M |
| FR-UC3-06 | 再提案の依頼に、結果と試行の履歴の要約（各回の変更の要点と指標）を含めること | M |
| FR-UC3-07 | 終了条件（成功、最大回数、改善が止まった、同じ失敗が続いた、形式違反が続いた、ユーザーの中断）で止めること | M |
| FR-UC3-08 | 最良だった状態を報告し、指定があればそれに戻すこと | M |
| FR-UC3-09 | 書き出す前の状態に確実に戻せること。ユーザーの git 履歴を勝手に変更しないこと | M |
| FR-UC3-10 | 各ラウンドの書き出したファイル、実行結果、指標を run ディレクトリに保存すること | M |
| FR-UC3-11 | 同じチャットを続ける場合は、変わっていないファイルを毎回全文送らないこと | M |
| FR-UC3-12 | 失敗の同一性の判定方法をループ定義で指定できること | M |
| FR-UC3-13 | AI からのファイル読み取り要求に、事前に許可した範囲だけ自動で応えること | S |
| FR-UC3-14 | 中断したループを、最後に完了したラウンドから再開できること | S |
| FR-UC3-15 | 実際に送信せずに、ループ定義の検証と 1 ラウンド目のプロンプトの確認ができること（`--dry-run`） | M |

## 5. UC4：コーディングループ（必須ではない）

- 必須要件には含めない。UC4 専用の機能（テストフレームワーク固有の処理、pytest の失敗の解析など）は作らない
- UC3 の仕組みで、ループ定義を書けば実現できることを確認する（spec-loop に UC4 をループ定義で書いた参考例を付録として載せる）
- テストの設定ファイル（`conftest.py`、`pytest.ini` など）を AI が書き換えて成功に見せかけることを防ぐため、ループ定義の検証で警告を出す（spec-security）

## 6. UC5：ファイル変換・生成の依頼

| ID | 要件 | 優先度 |
|---|---|---|
| FR-UC5-01 | コマンドラインから入力ファイルと要求を渡し、結果をファイルで受け取れること（`llmc convert`、`llmc ask -i ... -o ...`） | M |
| FR-UC5-02 | テキストの結果（CSV など）は回答のテキストから保存できること（方式 A） | M |
| FR-UC5-03 | バイナリの結果（.docx、.png など）を受け取れること。方式は spec-convert で選定する（ダウンロード B、手元の変換 C） | M |
| FR-UC5-04 | 入力の渡し方（本文に埋め込む・添付）を、サイズと機能の有無に応じて選べること | M |
| FR-UC5-05 | 大きな入力は、AI に変換スクリプトを出させて手元で実行する方式に切り替えられること。実行前の確認を必須とすること | M |
| FR-UC5-06 | 非対話モードで AI 作成のスクリプトを実行するのは、事前に承認したレシピ（スクリプトのハッシュで固定）か、明示的なフラグがある場合のみとし、どちらも無ければ専用の終了コードで止めること | M |
| FR-UC5-07 | 出力を検証し（CSV として読める、.docx・画像として開けるなど）、失敗したらエラーを添えて作り直しを依頼すること | M |
| FR-UC5-08 | 保存先は、コマンドを実行したディレクトリか `-o` で指定した場所に限ること。既存のファイルは、明示的な指定が無い限り上書きしないこと | M |
| FR-UC5-09 | 定型の変換を名前付きのレシピとして登録し、再利用できること | S |

## 7. 非機能要件

| ID | 区分 | 要件 |
|---|---|---|
| NFR-01 | 性能 | デーモン稼働中なら、`llmc ask` の送信開始までのオーバーヘッドは 2 秒以内（ブラウザ起動を含まない） |
| NFR-02 | 性能 | デーモンの初回起動（ブラウザ起動と画面の準備完了）は 30 秒以内を目標とする |
| NFR-03 | 信頼性 | 途中で切れた回答や、未完のファイルを書き込まないこと（誤書き込みゼロを目標とし、テストで確認する） |
| NFR-04 | 信頼性 | ファイルの書き込みは、1 回の回答の分を全部書くか、まったく書かないかのどちらかにすること |
| NFR-05 | 信頼性 | デーモンやブラウザが異常終了しても、ロックが残って次の実行を妨げないこと |
| NFR-06 | 安全性 | 書き込み・読み取りは許可リスト方式。変更禁止の判定は正規化後に行い、Windows 固有のパスの抜け道（大文字小文字、末尾のドットや空白、代替データストリーム、予約デバイス名、短い名前、リンク）をふさぐこと |
| NFR-07 | 安全性 | ブラウザのプロファイル、ログ、記録は作業リポジトリの外（ユーザーごとのデータディレクトリ）に置き、権限を本人だけに絞ること |
| NFR-08 | 安全性 | デーモンへの接続は本人のプロセスからに限ること |
| NFR-09 | 互換性 | 文字コード（UTF-8、BOM 付き UTF-8、Shift_JIS）と改行コード（LF、CRLF）を元のファイルに合わせて保持すること |
| NFR-10 | 互換性 | 日本語を含む入出力が、PowerShell 5.1 と cmd.exe のどちらでも文字化けしないこと（設定手順が必要な場合は手順を示し、`llmc doctor` で確認できること） |
| NFR-11 | 保守性 | 画面の変更には、コードではなくサイト別プロファイルの修正で対応できることを基本とする |
| NFR-12 | 保守性 | 書式の規則の原本は 1 つとし、プロンプト用とエージェントの指示文用の両方をそこから作ること |
| NFR-13 | 可観測性 | すべての実行に ID を振り、デーモンとクライアントのログを ID で突き合わせられること |
| NFR-14 | 利用量 | 社内規程で利用頻度に上限がある場合に備え、送信回数の上限（時間あたり・日あたり）を設定できること |
| NFR-15 | 導入 | 管理者権限なしで、venv への導入とユーザー権限の設定だけで使えること |

## 8. スコープ外

- OpenAI 互換のエンドポイントの公開（アダプタの構造上、後から追加できる余地は残す）
- 並列リクエスト（複数タブ・複数ブラウザ）
- 複数ユーザーでの共有、チーム配布、インストーラ
- Linux・macOS 対応、PowerShell 7 専用の機能
- w3m などのテキストブラウザ方式、Cline や OpenCode などの既存エージェントをフロントエンドにする方式
- 差分形式（パッチ）によるファイル更新（v1 では全文置換のみ。spec-file-protocol 参照）
- ふだん使いのブラウザとの並行利用、プロファイルの共有

## 9. 要確認事項（社内規程など。詳細は open-questions.md）

- 画面の自動操作が社内規程で許されるか
- 利用頻度の上限
- チャットに送ってよい情報の範囲（ソースコード、設定ファイル、ログ、社内ホスト名、個人情報）
- AI が書いたコードやスクリプトを社内 PC で実行してよいか
