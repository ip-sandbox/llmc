# 変換仕様（UC5）

> **状態: 下書き**（plan 5.6 の 6 の前倒し、2026-11-28）。方式 B（ダウンロード）と添付は、組織版で使えるかどうかが分からない。PoC-5 の (d) で確かめてから確定する（plan 5.6 の 8）。確かめる項目は 13 章にまとめた。方式 A と C は、これまでの PoC の結果（出力の上限、文字の変化、実行器）だけで決められる範囲を書いた。

## 1. 範囲と前提

- UC5「ファイル変換・生成の依頼」の動きを定める。具体的には、コマンド、方式の選び方、入力の渡し方、規則の文面、スクリプトの実行と承認、出力の検証、保存、レシピ、記録
- ファイルの書式・解析・書き込みの手順は spec-file-protocol に従う。実行器は spec-loop 7 章、規則の原本は spec-agent、画面操作は spec-browser-driver、マスキングと脅威モデルは spec-security（未作成）に従う
- PoC で分かった制約のうち、変換の設計に効くもの

| 制約 | 値（PoC） | 本書での扱い |
|---|---|---|
| 1 回の回答の出力の上限 | 約 8,000 文字（個人版）。1 ファイルの中身の上限は 7,000 文字（spec-file-protocol 11 章） | 方式 A で作れるのは 7,000 文字までの出力。それより大きい出力は方式 C（3 章） |
| 1 回の送信の上限 | 60,000 文字（`max_input_chars`） | 入力を本文に埋め込めるかどうかの判定（4 章） |
| 上限を超えたときの AI | 個人版は途中を `...` にして書き切る。組織版は断る | どちらも `E_TOO_LARGE`。方式 C へ切り替える（3.3） |
| 文字の変化 | `[名前]:` が消える、URL・`<` `>` が送信の時点で変わる（spec-file-protocol 9.7） | 方式 A の出力にも C のスクリプトにも、代わりの記号と実体参照の戻しをかける。Python の `if flags[i]:` も `[名前]:` の形に当たる（6.3） |
| コピーの HTML | フェンスに言語名を書くと崩れる | スクリプトも言語名なしのフェンスで出させる（spec-file-protocol 4.3） |
| 添付 | `.ps1` などは受け付けない。アップロードしたファイルは利用者の OneDrive にコピーされる（review-related-projects 3 章） | 添付は既定で使わない（4.2） |
| ダウンロード | `a[download]`（`blob:`）を押すと Edge が落ちた報告がある | 押さずに、ページの中で取り出す（3.4。PoC-5） |
| 権限 | 管理者権限なし。venv にはパッケージを入れられる（plan 前提 3） | 方式 C は venv の Python とそのライブラリで動かす。llmc はパッケージを自動では入れない（6.2） |

## 2. コマンド

```powershell
llmc convert -i data.csv -o data.json "列名を英語のキーにした JSON の配列にして"
llmc convert -i a.csv -i b.csv -o merged.xlsx "2 つを ID でつないで 1 枚のシートに"
llmc convert -r monthly-report -i 2026-11.csv -o 2026-11.docx
llmc ask -i notes.md -o notes.csv "表の部分だけを CSV に"
```

| 引数 | 意味 |
|---|---|
| `-i <パス>` | 入力ファイル。複数指定できる（既定の上限 10 個）。無くてもよい（「〇〇の雛形を作って」など） |
| `-o <パス>` | 出力ファイル。**1 回の変換で 1 つ**（v1）。拡張子で出力の種類を決める（5 章）。省略した場合は、入力の名前と `--to` の拡張子から作り、カレントディレクトリに置く |
| `--to <拡張子>` | `-o` を省いたときの出力の種類 |
| 要求の文 | 何をするか。レシピを使うときは省ける |
| `-r <レシピ>` | 名前付きのレシピを使う（9 章） |
| `--method auto\|text\|script\|download` | 方式（3 章）。既定 `auto` |
| `--force` | 既存の出力を上書きする（8 章） |
| `--approve-exec` | 非対話の実行で、AI が書いたスクリプトの実行を許す（7.3） |
| `--non-interactive` | 確認の入力を待たない（stdin が端末でなければ自動でこの扱い。spec-shell-integration） |
| `--encoding`・`--newline` | テキストの出力の文字コードと改行（8.2） |
| `--attach` | 入力を本文に埋め込まず、画面の添付機能で渡す（4.2。対応するサイトだけ） |
| `--save-recipe <名前>` | 成功したら、その変換をレシピとして保存する（9.3） |
| `--json` | 結果を JSON で stdout に出す（10 章） |
| `--dry-run` | 方式の選択と、送る本文を示すだけで、送信も実行もしない |

- `llmc ask` に `-o` を付けた場合は、`llmc convert` と同じ処理になる（FR-UC5-01）。`-o` の無い `llmc ask -i` は、回答を stdout に出すだけで、ファイルは書かない（UC2）
- stdin からの入力（`Get-Content x.csv | llmc convert -o y.json ...`）は、名前 `stdin.txt` の入力として扱う。PowerShell 5.1 のパイプで日本語が崩れる問題（plan 前提 4）があるので、`-i` を勧める

## 3. 方式

### 3.1 3 つの方式

| 方式 | 名前（`--method`） | 内容 | 向いている出力 | 状態 |
|---|---|---|---|---|
| A | `text` | AI が出力ファイルの全文を、書式 llmc/1 のファイルブロックで回答に書く。llmc はそれを保存する | 7,000 文字までのテキスト（CSV、JSON、YAML、Markdown、SVG など） | PoC の結果だけで決められる |
| C | `script` | AI が変換のスクリプト（Python）を書き、llmc が手元で実行して出力を作る。AI には入力の見本だけを送る | 大きなテキスト、バイナリ（.xlsx、.docx、.png など）、大きな入力 | 実行器は PoC-4 で確認済み。AI がスクリプトを書けることは UC3 と同じ |
| B | `download` | AI がサイトの機能（コードインタープリター、文書の作成）でファイルを作り、llmc がダウンロードする | バイナリ | **未確認**（PoC-5）。既定では選ばない |

- 方式の名前は requirements（A、B、C）に合わせた。説明の順は、よく使う順（A → C → B）にした
- B を既定にしない理由: 組織の Copilot Chat で使えるかが分からない。作られたファイルの中身を llmc が確かめる手段が、出力の検証（5 章）しかない。ファイルが OneDrive・SharePoint に保存される場合は、組織のデータの置き場所に llmc が関わることになる（spec-security）

### 3.2 自動の選択（`--method auto`）

上から順に、最初に当てはまった行の方式を使う。

| 条件 | 方式 | 理由 |
|---|---|---|
| レシピで方式が決まっている | レシピの方式 | 同じ条件で繰り返すため |
| 出力の種類がバイナリ（5 章の表） | C | A ではバイナリを書けない（`E_BINARY_TARGET`）。B は既定では選ばない |
| 入力に、本文に埋め込めないもの（バイナリ）がある | C | 入力の見本を llmc が作れるのは C だけ（4.3） |
| 入力の合計（埋め込んだ後の文字数）が `convert.embed_max_chars`（既定 40,000）を超える | C | 規則・要求・本文を合わせて、1 回の送信の上限（60,000）に収めるため |
| 入力の合計が `convert.text_max_input_chars`（既定 6,000）を超える | C | 変換の出力は、入力と同じくらいの大きさになることが多い。出力の上限（7,000）を超えそうなものは、最初から C にする |
| それ以外 | A | — |

- 「要約して」「件数を数えて」のように、入力が大きくても出力が小さい依頼は、`--method text` で A を指定できる。この場合、入力が `convert.embed_max_chars` 以下なら A で送る
- `--dry-run` で、選んだ方式と、その理由（表のどの行に当たったか）を示す

### 3.3 方式 A から C への切り替え

A で送った回答が出力の上限を超えた場合（`E_TOO_LARGE`、`E_ELIDED`、組織版の断り。spec-file-protocol 11.1）は、同じ依頼を A で繰り返さない。

| 実行の種類 | 動作 |
|---|---|
| 対話 | 「出力が大きすぎるので、変換のスクリプトを書いてもらい手元で実行します。よいですか」と確かめ、`y` なら C で依頼し直す |
| 非対話で `--approve-exec` あり | C で依頼し直す（切り替えたことを stderr と JSON に出す） |
| 非対話で `--approve-exec` なし | `EXIT_NEEDS_APPROVAL` で止める。**C の依頼は送らない**（利用量を無駄にしない） |

### 3.4 方式 B（下書き。PoC-5 の後に確定する）

1. 規則の `binary` 節（spec-agent）で、「サイトの機能でファイルを作り、ダウンロードできる形で返す」ことを依頼する。エージェント `llmc-convert`（spec-agent 5.1。コードインタープリターが有効）を使える場合は、それを使う
2. ドライバが回答の中のダウンロードのリンクを `TurnResult.artifacts` として返す（spec-browser-driver 7.3）
3. クライアントがデーモンに `download` を要求する。デーモンは、リンクを押さずに（`blob:` のリンクで Edge が落ちた報告があるため）、ページの中で `fetch` してファイルを取り出し、`daemon\downloads\` に置く（spec-daemon）
4. クライアントが出力を検証し（5 章）、保存先へ移す（8 章）

- 成果物が無い、複数ある、名前の拡張子が違う場合はエラーにする（`E_NO_ARTIFACT`・`E_MULTIPLE_ARTIFACTS`・`E_ARTIFACT_TYPE`）。作り直しの依頼は 1 回まで
- エージェントが使えない場合（spec-agent 8.2）は、`--method auto` なら C に切り替え、`--method download` ならエラーにする
- 人が送信する方式（spec-browser-driver 13 章）では B は使えない（ダウンロードを llmc が受け取れないため）

## 4. 入力の渡し方

### 4.1 本文に埋め込む（既定）

- 方式 A では、入力の全文を文脈として埋め込む（spec-file-protocol 5 章の `LLMC-CTX`）。送る前の変換は spec-loop 5.1 と同じ順にする: マスキング → 代わりの記号と `&lt;` の `&` の置き換え（spec-file-protocol 9.7） → 空行の代わりの行（9.6）
- **AI に見せるパスは、llmc が付けた名前だけにする**。入力は `input1.csv`、`input2.csv`…（元の拡張子を残す）、出力は `output.<拡張子>` とする。利用者のディレクトリの名前（利用者名を含むことがある）を送らないためと、AI がパスを書き誤る余地をなくすため。元の名前に意味がある場合（列の説明になっているなど）は、要求の文に書いてもらう
- 元から `⟦U+` を含む入力は送れない（spec-file-protocol 9.7）。方式 A では止め、方式 C では見本から外して「見本に含められない行がある」と伝える

### 4.2 添付（`--attach`。下書き）

- サイトのプロファイルの `capabilities.attachments` が有効で、`--attach` を指定したときだけ使う。既定では使わない
- 理由: アップロードしたファイルは利用者の OneDrive にコピーされる（review-related-projects 3 章）。チャットの本文とは別の場所に、別の保存期間で残る。組織の規程で許されるかは spec-security と open-questions で扱う
- 添付するのは、クライアントがマスキングしたうえで `daemon\staging\` に置いた一時ファイルだけ（architecture 1 章）。拡張子が受け付けられないもの（`.ps1` など）は `.txt` を付ける
- AI が添付を全文読むのか、要約や検索だけなのかは分からない（spec-browser-driver 9 章）。全文を読んだかを確かめる手段が無いので、添付を使った変換の出力は、検証（5 章）で必ず確かめる。PoC-5 で調べる

### 4.3 入力の見本（方式 C）

方式 C では、AI に入力の全体を送らず、スクリプトを書くのに必要なだけの見本を送る（FR-UC5-05）。入力の全体は、スクリプトが手元で読む。

| 入力の種類 | 見本 |
|---|---|
| テキスト（CSV、TSV、JSON Lines、ログなど） | 先頭 `sample.head`（既定 30）行と末尾 `sample.tail`（既定 5）行。行数、文字コード（`utf-8`・`utf-8-sig`・`cp932`）、改行、区切り文字の推定も添える |
| JSON（1 つの値） | 先頭から `sample.max_chars`（既定 4,000 文字）まで。構造（キーの一覧、配列の長さ）を llmc が要約して添える |
| .xlsx（`openpyxl` があるとき） | シートの名前の一覧、各シートの大きさ、先頭 `sample.head` 行の値 |
| .docx（`python-docx` があるとき） | 段落と表の数、先頭の段落の数個、見出しの一覧 |
| その他のバイナリ、ライブラリが無いとき | 名前、拡張子、大きさだけ |

- 見本にもマスキングと代わりの記号をかける
- 見本は `LLMC-CTX path="input1.csv" range=head=30 ...` の形で送る（一部だけなので、書き換えは許さない。spec-file-protocol 5 章の `range`）。方式 C で AI が書くのはスクリプトだけなので、入力の書き換えは起きない
- **残るリスク**: スクリプトが失敗したときに戻す stderr（7.4）には、入力の行がそのまま出ることがある（Python の例外のメッセージなど）。マスキングをかけ、`feedback.stderr_tail`（既定 40 行）に絞る。`--no-feedback-output` で、終了コードと検証の結果だけを戻すようにできる

## 5. 出力の種類と検証

出力は、保存する前に必ず検証する（FR-UC5-07）。方式によらず同じ検証をかける。

| 拡張子 | 種類 | 検証 |
|---|---|---|
| `.csv`・`.tsv` | テキスト | 指定の文字コードで復号できる。`csv` モジュールで最後まで読める。全行の列の数が同じ（違えば行番号を示す） |
| `.json` | テキスト | `json.loads` で読める |
| `.jsonl` | テキスト | 全行が `json.loads` で読める |
| `.yaml`・`.yml` | テキスト | `yaml.safe_load` で読める（PyYAML は llmc が使うので必ずある） |
| `.xml`・`.svg` | テキスト | 外部の実体を読まない設定で構文を解析できる |
| `.md`・`.txt`・`.html`・その他のテキスト | テキスト | 復号できる |
| `.py`・`.ps1` など、コード | テキスト | 復号できる。`.py` は `compile()` が通る |
| `.xlsx`・`.docx`・`.pptx` | バイナリ | ZIP として壊れていない。`[Content_Types].xml` と、種類ごとの本体（`xl/workbook.xml` など）がある。ライブラリがあれば開けること（`openpyxl.load_workbook` など）も確かめる |
| `.png`・`.jpg`・`.gif` | バイナリ | ファイルの先頭のマジックナンバー。`Pillow` があれば `verify()` |
| `.pdf` | バイナリ | 先頭が `%PDF-`、末尾付近に `%%EOF` |
| 表に無い拡張子 | バイナリ | 空でないことだけ。`--validate-cmd` かレシピの `validate.command` で検証を足せる |

- 共通: 空でない。大きさが `convert.max_output_bytes`（既定 50 MB）以下
- 利用者の検証（任意）: レシピの `validate.command`（argv の配列。`{output}` を出力の一時ファイルのパスに置き換える）。終了コード 0 で合格。spec-loop 7 章の実行器で動かす。これは利用者が書いたコマンドなので、承認（7.3）の対象にしない
- **検証は「形として正しい」ことしか確かめない**。中身が要求どおりかは確かめられないので、対話の実行では、保存の前にテキストの出力は先頭の数十行を、バイナリの出力は検証の結果の要約（シートの数、行の数、ページの数など、ライブラリで分かる範囲）を示す
- 検証に失敗したら、エラーの文（行番号、例外の種類と 1 行目、どの検査に落ちたか）を添えて作り直しを依頼する。回数は `convert.retries`（既定 2）まで。超えたら `EXIT_CONVERT_FAILED` で止め、最後の出力は run ディレクトリにだけ残す（保存先には書かない）

## 6. 規則の文面（spec-agent の `binary` 節と、変換用の節）

### 6.1 方式 A

規則の原本（spec-agent 2.1）のうち、`role`・`plan`・`file_block`・`chars`・`done`・`style`・`no_tools` を使う。変換用に次を足す。

```text
（要求の文）

入力: input1.csv（下の LLMC-CTX）
出力: output.json を 1 つだけ、base=new の全文で書いてください。
- 出力のファイル以外は書かないでください（読み取り要求もしません）
- ファイルをツールで作らず、テキストで書いてください
```

- 出力のファイルは計画（`LLMC-PLAN write="output.json"`）に 1 つだけ書かれ、ファイルブロックも 1 つだけであることを確かめる。他のパスへの書き込み・削除・読み取り要求は `E_PATH_DENIED` として、出し直しを依頼する（許可リストは `output.<拡張子>` だけ）
- 解析と文字の戻し（代わりの記号、`&lt;` の戻し、空行の代わりの行）は、ループと同じ（spec-file-protocol 6・9 章）
- 回答にファイルブロックが無く、ダウンロードのリンク（`TurnResult.artifacts`）がある場合は `E_TOOL_ARTIFACT` として、テキストで書くよう 1 回だけ依頼する（方式 C でも同じ）。リンクのファイルはダウンロードしない。続く場合は、stderr に「このサイトはファイルを作れるようです。`--method download` を試せます」と示す（方式 B が確定するまで）

### 6.2 方式 C

```text
（要求の文）

この依頼は、手元で実行する Python のスクリプトで行います。convert.py を base=new の全文で書いてください。
- 実行のしかた: python convert.py --input input1.csv --output output.xlsx
  （--input は入力の数だけ、指定の順に並ぶ。パスはこの名前のまま渡す）
- 使える Python: 3.11。標準ライブラリと、次のモジュールだけ: openpyxl, python-docx
- 入力の見本は下の LLMC-CTX（全体は N 行。見本は先頭 30 行と末尾 5 行）
- 入力ファイルを変更しない。--output 以外のファイルを書かない。ネットワークを使わない。別のプログラムを起動しない
- 入力の文字コードは utf-8-sig（llmc の推定）。違う場合に備えて、読めなければ cp932 も試す
- 失敗したときは、理由を stderr に 1 行で書き、終了コード 1 で終わる
```

- 「使えるモジュール」は、llmc が実行に使う Python（6.4）で `importlib.util.find_spec` を調べて書く。候補の一覧は設定（`convert.python_modules`、既定 `openpyxl`・`python-docx`・`python-pptx`・`Pillow`・`reportlab`・`pandas`）
- 出力の種類に必要なモジュールが無い場合（.docx なのに `python-docx` が無い）は、送る前に止めて、入れ方（`.venv\Scripts\python.exe -m pip install python-docx`）を示す。**llmc はパッケージを自動では入れない**。AI が「〇〇を入れてください」と書いてきても同じ
- 回答の計画は `write="convert.py"` だけ。他の書き込みは方式 A と同じく拒否する

### 6.3 スクリプトの文字の扱い

- AI が書くスクリプトにも、`[名前]:` の規則（spec-file-protocol 9.7）が効く。Python では `if flags[i]:`・`d[key]:`・`x[0]:` などがこの形に当たり、**描画で `:` と後ろの空白が消える**。規則の `chars` 節（`[名前]` の直後の `:` を `⟦U+003A⟧` と書く）は C でも必ず送る
- 守られなかったときは、6.4 の `compile()` で構文の誤りとして見つかることが多い（`if flags` の後ろが消えるため）。見つかったら、`W_SUSPECT_STRIPPED` を添えて出し直しを依頼する（承認の前に行う。利用者に壊れたスクリプトを見せない）
- `<` `>` は送信の時点で `&lt;` `&gt;` になるが、AI が新しく書くスクリプトの `<` は回答でそのまま返る（spec-file-protocol 9.7）。回答のファイルの中身の `&lt;` は `<` に戻す。スクリプトに `&lt;` という文字列そのものが要る場合（HTML を出力する変換など）は、`W_ENTITY_RESTORED` として承認の画面で示す

### 6.4 実行する前の検査

AI のスクリプトを受け取ったら、承認（7 章）の前に次を行う。

| 検査 | 内容 | 失敗のとき |
|---|---|---|
| 構文 | `compile(source, "convert.py", "exec")` | 出し直しを依頼（承認を求めない） |
| モジュール | `import` と `from ... import` の一覧（`ast` で取る）が、標準ライブラリと「使えるモジュール」に収まる | 出し直しを依頼 |
| 注意する呼び出し | `subprocess`・`os.system`・`os.popen`・`socket`・`urllib`・`http.client`・`requests`・`ctypes`・`winreg`・`shutil.rmtree`・`os.remove`・`eval`・`exec`・`__import__`・`importlib` | 既定（`convert.script.deny`）では出し直しを依頼する。承認の画面にも一覧を示す |
| 大きさ | `convert.script.max_chars`（既定 7,000 文字。1 ファイルの中身の上限と同じ） | — （上限を超えたものは spec-file-protocol で既に `E_TOO_LARGE`） |

- **この検査は砂場（サンドボックス）ではない**。文字列を組み立てて呼ぶ、`getattr` を使うなどで、検査はすり抜けられる。スクリプトは利用者の権限で動き、利用者が読めるファイルはすべて読める（NFR-16、architecture 1 章の 6）。検査は AI のうっかりを見つけるためのもので、守りの中心は承認（7 章）である。spec-security の脅威モデルに書く

## 7. スクリプトの実行

### 7.1 作業の場所

```text
%LOCALAPPDATA%\llmc\runs\convert\<run ID>\work\
  convert.py          AI が書いたスクリプト（代わりの記号を戻した後）
  input1.csv          入力の写し（元のファイルは渡さない）
  output.xlsx         スクリプトが書く出力
```

- 入力は写しを渡す。スクリプトが誤って入力を書き換えても、元のファイルは変わらない
- 作業ディレクトリ（`cwd`）は `work\`。スクリプトにはこの中の名前だけを渡す（4.1 の名前と同じ）
- 実行の後に `work\` を走査し、`output.<拡張子>` 以外に増えた・変わったファイルがあれば警告に示す（`W_EXTRA_FILES`。保存はしない）。`work\` の外の変化は検出しない（spec-loop 8.6 のワークスペースの走査は、変換では行わない。変換にはワークスペースが無いため）

### 7.2 起動

- spec-loop 7 章の実行器を使う。シェルを通さず、`[<Python>, "-I", "convert.py", "--input", "input1.csv", ..., "--output", "output.xlsx"]` で起動する
  - `<Python>`: 設定 `convert.python`。既定は llmc 自身の venv の `python.exe`。変換用に別の venv を作って指定してもよい（llmc の依存と、変換のライブラリを分けたい場合）
  - `-I`: 環境変数 `PYTHONPATH` と利用者の site-packages を読まない
- ジョブオブジェクトに入れ、`convert.timeout_s`（既定 120 秒）で終わらせる。標準入力は空、ウィンドウは作らない、`PYTHONUTF8=1`（spec-loop 7.1・7.3・7.4）
- 終了コード 0 で、`output.<拡張子>` があれば、出力の検証（5 章）へ進む

### 7.3 承認（FR-UC5-05・06）

AI が書いたスクリプトは、利用者の承認があるときだけ実行する。

| 実行の種類 | 動作 |
|---|---|
| 対話 | スクリプトの全文（ページャ）、使うモジュール、注意する呼び出し（あれば）、入力と出力の名前、ハッシュを示し、実行してよいか確かめる。既定の答えは「いいえ」 |
| 非対話で、レシピに固定したスクリプトがあり、ハッシュが一致する | 実行する（9.2）。**AI には何も送らない** |
| 非対話で `--approve-exec` あり | 6.4 の検査に通れば実行する |
| 非対話で、どちらも無い | 方式 C になると分かった時点で、**送信する前に** `EXIT_NEEDS_APPROVAL` で止める |

- 作り直し（5 章の検証の失敗、7.4）で新しいスクリプトになったら、承認もし直す。対話では、前のスクリプトとの差分を示す
- ハッシュは、スクリプトのバイト列（改行を LF にそろえたもの）の SHA-256。承認の記録は、レシピに固定した場合だけ残す（9.2）。1 回限りの変換の承認は記録しない

### 7.4 失敗したとき

| 失敗 | 作り直しの依頼に添えるもの |
|---|---|
| 終了コードが 0 でない | 終了コード、stderr の末尾（マスキング後、`feedback.stderr_tail` 行まで） |
| 時間切れ | 「120 秒で終わらなかった」。入力の行数 |
| 出力が無い | 「output.xlsx が作られなかった」。`work\` に増えたファイルの名前 |
| 検証に落ちた | 5 章の検証のエラーの文 |

- 作り直しは、同じ会話で続ける（スクリプトと見本は前のターンにあるので、全文を送り直さない。ただし spec-file-protocol 5.1 の `resend_before_edit` に従い、書き換えの元にするスクリプトは全文を送る）
- 回数は `convert.retries`（既定 2）まで。同じエラーの文が 2 回続いたら、回数が残っていても止める（spec-loop 8.4 と同じ考え方）

## 8. 保存（FR-UC5-08）

### 8.1 保存先と上書き

- 保存先は `-o` の場所か、カレントディレクトリに限る（`-o` の無いとき）。`-o` に書けるのは 1 つのファイルだけで、spec-file-protocol 8 章のパスの検査（正規化、常時禁止、実パスの確認）をかける
- 既存のファイルがあれば、既定では書かない（spec-file-protocol 10.1 の `deny_existing`。`E_EXISTS` → `EXIT_EXISTS`）。`--force` で上書きする。**この確認は送信の前に行う**（変換が済んでから断ると、利用量が無駄になるため）。送信の後に同じ名前のファイルができていた場合も、もう一度確かめる
- 書き込みは spec-file-protocol 10 章の手順（ジャーナル、スナップショット、`ReplaceFileW`）で行う。上書きしたファイルは `llmc undo` で戻せる
- 方式 C・B の出力は、`work\` や `daemon\downloads\` から、検証の後に同じ手順で保存先へ書く（移動ではなく書き込み。ジャーナルに載せるため）

### 8.2 テキストの文字コードと改行

- 方式 A の出力は、新規ファイルとして spec-file-protocol 9.3 の既定（その他は UTF-8・BOM なし・LF）で書く。`--force` で既存のファイルを上書きする場合は、既存のファイルの文字コードと改行に合わせる（9.1・9.4）
- `--encoding utf-8|utf-8-sig|cp932` と `--newline lf|crlf` で指定できる。Excel で開く CSV は、`utf-8-sig` か `cp932` でないと文字化けするので、出力が `.csv` で指定が無いときは、対話の実行で一度だけ注意を出す（`convert.csv_encoding` を設定すれば出さない）
- 方式 C・B の出力はバイト列のまま書く（文字コードはスクリプトかサイトが決める）。方式 C では、規則で「CSV は utf-8-sig で書く」などを指定できる（レシピの `output.encoding` を規則の文に入れる）

## 9. レシピ（FR-UC5-09）

### 9.1 形式

```yaml
# %LOCALAPPDATA%\llmc\recipes\monthly-report.yaml
llmc_recipe: 1
name: monthly-report
description: 月次の売上の CSV を、集計の表を付けた Word の報告書にする
request: |
  売上の CSV から、店舗ごとの合計と前月比の表を作り、
  見出し「月次売上」の下に置いた Word の文書にしてください。
inputs:
  - ext: [.csv]
    encoding: auto
output:
  ext: .docx
method: script            # text | script | download
validate:
  command: null           # 任意。["python", "check_report.py", "{output}"] など
script:                   # method: script で固定したスクリプト（9.2）
  file: monthly-report.convert.py
  sha256: 9f2c...e1
  python_modules: [python-docx]
  approved_at: 2026-11-28T10:12:00
mask: []                  # この変換だけのマスキング規則（spec-security）
```

- 置き場所は `%LOCALAPPDATA%\llmc\recipes\`（利用者のもの）か、`-r` にパスを書いたもの（作業リポジトリの中に置いてもよい）
- 作業リポジトリに置いたレシピの `script.approved_at` は信用しない。承認の記録は `%LOCALAPPDATA%\llmc\approvals\` にだけ置き（spec-loop 3.3 と同じ）、レシピの中の値は表示用とする。他人が書いたレシピのハッシュを、そのまま承認済みとして扱わないため

### 9.2 固定したスクリプト

- `script` があるレシピで、承認の記録とハッシュが一致すれば、**AI に送らずに手元で実行する**。同じ形の入力を毎月変換する、といった使い方では、利用量を使わず、毎回同じ結果になる
- 入力の形が変わってスクリプトが失敗した（7.4）場合
  - 対話: 「AI に直してもらいますか」と確かめる。直したスクリプトは新しいハッシュになるので、承認し直し、レシピを更新するか確かめる
  - 非対話: `EXIT_CONVERT_FAILED` で止める。`--approve-exec` があっても、固定したスクリプトを黙って差し替えない
- ハッシュが一致しない（スクリプトのファイルが書き換えられた）ときは、実行しない。対話では差分を示して承認し直すか確かめる。非対話では `EXIT_NEEDS_APPROVAL`

### 9.3 保存（`--save-recipe`）

- 変換が成功したら、要求の文、入力と出力の拡張子、方式、（方式 C なら）最後に成功したスクリプトとそのハッシュを、レシピとして保存する
- 方式 C で保存するときは、承認の記録も作る（その場で利用者が承認したスクリプトなので）。非対話で `--approve-exec` を使った変換からは、スクリプトを固定したレシピを作らない（承認を経ていないため。`script` の無いレシピだけを作り、stderr に知らせる）
- `llmc recipe list`・`show <名前>`・`approve <名前>`・`remove <名前>` で管理する

## 10. 記録と出力

### 10.1 run ディレクトリ

```text
%LOCALAPPDATA%\llmc\runs\convert\<run ID>\
  request.json        コマンドの引数、選んだ方式と理由、入力の名前・大きさ・ハッシュ（元のパスは記録する。本人だけが読める場所なので）
  turns\01\           送った本文（マスキング後）、解析の結果
  work\               7.1（方式 C）
  output.validate.json
  result.json         10.2 と同じ内容
```

- 権限、保存の期間（既定 30 日）、`llmc runs prune` はループと同じ（spec-loop 9 章）
- 入力の写し（`work\input1.csv`）は、変換が成功したら消す（`--keep-work` で残す）。入力に機密が含まれることがあり、元の場所の権限より広く残さないため（`%LOCALAPPDATA%` は本人だけの権限だが、元のファイルを消しても写しが残ってしまう）

### 10.2 結果（`--json`）

```json
{
  "status": "ok",
  "exit_code": 0,
  "method": "script",
  "method_reason": "output_binary",
  "output": "C:\\work\\2026-11.docx",
  "output_bytes": 18234,
  "validation": {"ok": true, "checks": ["zip", "content_types", "python-docx"]},
  "sends": 2,
  "retries": 1,
  "script_sha256": "9f2c...e1",
  "recipe": null,
  "conversation": "https://...",
  "warnings": ["W_EXTRA_FILES"]
}
```

- 標準出力には、`--json` が無ければ何も出さない（出力はファイルにある）。進捗と警告は stderr（FR-UC2-03）

### 10.3 終了コード（名前。番号は spec-shell-integration）

| 名前 | 場面 |
|---|---|
| `EXIT_NEEDS_APPROVAL` | 非対話で、スクリプトの実行に承認が要る（3.3・7.3・9.2） |
| `EXIT_EXISTS` | 出力が既にある（8.1） |
| `EXIT_CONVERT_FAILED` | 作り直しの回数を使い切った、固定したスクリプトが失敗した（5 章・7.4・9.2） |
| `EXIT_MISSING_MODULE` | 出力に必要なモジュールが、実行に使う Python に無い（6.2） |
| `EXIT_NEEDS_HUMAN` | 人が送信する方式を、非対話で使おうとした（spec-loop 12 章と同じ） |
| `EXIT_RATE_LIMITED`・`EXIT_LOGIN_REQUIRED` | ループと同じ（spec-loop 11 章、spec-auth） |

## 11. 人が送信する方式

- 方式 A と C は、人が送信する方式（個人版）でも動く。llmc がクリップボードに本文を入れ、利用者が貼り付け・送信・回答のコピーをする（spec-browser-driver 13 章）。作り直しのたびに、同じ操作が要る
- 方式 B と添付は使えない
- 非対話の実行では使わない（`EXIT_NEEDS_HUMAN`）。ただし、固定したスクリプトのレシピ（9.2）は送信が無いので、非対話でも動く

## 12. 利用量

- 1 回の変換の送信の数は、最初の依頼 1 回と、作り直しの `convert.retries`（既定 2）回と、A から C への切り替え（3.3）1 回までなので、多くて 4 回
- 送信はデーモンが数える（NFR-14、spec-daemon 7 章）。1 時間・1 日の上限に当たったら、ループと同じく止める（`EXIT_RATE_LIMITED`）
- 方式 C は、入力を全部送る A より送る文字数が少ない。大きな入力では、利用量の面でも C が有利になる

## 13. PoC で確かめること（PoC-5 の (d)、組織版）

| 項目 | 確かめること | 決まるもの |
|---|---|---|

| 成果物の置き場所 | 作られたファイルが OneDrive・SharePoint に保存されるか | spec-security。方式 B を既定にしない理由の確認 |
| 添付 | 添付の上限（大きさ・個数・拡張子）、`.csv`・`.txt` を AI が全文読むか（先頭と末尾に合言葉を入れて確かめる）、アップロード先 | 4.2 を残すか。`capabilities.attachments` の値 |
| 方式 A の出力の上限（組織版） | 7,000 文字に近い CSV を A で出させて、全部出るか（PoC-6 の出力 400・600 行と同じ確認） | `convert.text_max_input_chars` の既定値 |
| 方式 C のスクリプト | 3 種類の依頼（CSV → .xlsx、CSV → .docx、10,000 行の CSV の集計）で、スクリプトが 1 回で動く率、6.4 の検査に当たる率、`[名前]:` の規則が守られる率 | `convert.retries` の既定値、6.2 の文面 |

- 方式 A と C の確認は、PoC-5 を待たずに、PoC-6・PoC-7 と同じ形の小さなスクリプトで行える
