# デーモン仕様

> **状態: 下書き**（plan 5.6 の 4、2026-11-28）。常駐の実際の振る舞い（画面のロック・RDP の切断・スリープ、利用者がウィンドウを閉じたとき、タスクスケジューラからの起動）は PoC-8 で確かめ、その結果で確定する（plan 5.6 の 6）。確かめる項目は 12 章にまとめた。

## 1. 範囲と前提

- デーモンは「チャットの 1 往復」だけを担う（architecture 1 章）。ブラウザ、ログインの状態、順番待ちのキュー、送信の数え上げを持つ。ワークスペースには触らない
- 1 利用者に 1 つ。`pythonw.exe` で動き、コンソールを持たない
- ブラウザは画面ありの Edge を最小化して常駐させる。組織の PC ではヘッドレスがポリシーで禁止されている（`HeadlessModeEnabled=false`）。**回避しない**
- 人が送信する方式（spec-browser-driver 13 章）はクライアントの中で動き、デーモンを使わない
- PoC で確かめたこと

| 項目 | 結果 | 本書での扱い |
|---|---|---|
| パイプの DACL | 標準ライブラリのパイプは Everyone と匿名に読み取りを許す。ctypes で本人と SYSTEM だけの DACL を付けられた（PoC-4 の H-12） | 3.1 |
| パイプの乗っ取り | `FILE_FLAG_FIRST_PIPE_INSTANCE` で、同じ名前のパイプが既にあれば作れない。クライアントは `GetNamedPipeServerProcessId` でサーバの所有者を確かめられた | 3.1 |
| pythonw と Playwright | `DETACHED_PROCESS` の pythonw から Playwright が動いた（H-13） | 2.1 |
| ジョブからの切り離し | 切り離しを許さないジョブの中からは、`CREATE_BREAKAWAY_FROM_JOB` で起動しても**ジョブの中に残った**（エラーにならない） | 2.1 |
| 最小化 | DevTools プロトコルの `Browser.setWindowBounds` で最小化でき、処理は間引かれなかった。組織版で最小化したまま送信から抽出まで取れた | 4.1 |

## 2. 起動と終了

### 2.1 起動

- クライアントは、要求を送る前にパイプにつなぐ。つながらなければデーモンを起動する（FR-COM-06）
  - `pythonw.exe -m llmc.daemon` を `DETACHED_PROCESS | CREATE_NEW_PROCESS_GROUP | CREATE_BREAKAWAY_FROM_JOB` で起動する。`CREATE_BREAKAWAY_FROM_JOB` が拒否された（エラー 5）ら、その旗を外して起動し直す
  - 起動の後、**デーモンがジョブの外に出られたかを確かめる**（`IsProcessInJob`）。ジョブの中に残った場合は、クライアントが終わるとデーモンも終わる恐れがあるので、警告する（「タスクスケジューラなどから使う場合は、先に `llmc daemon start` を別に実行しておく」）。止めはしない
  - 起動を待つのは最大 60 秒（NFR-02 の目標は 30 秒）。デーモンは、パイプを作った時点で `starting` を返せるようにし、ブラウザの準備ができたら `ready` にする
- 利用者が明示して起動する: `llmc daemon start`（前面のコンソールで動かす `--foreground` は開発用）
- ログオン時の自動起動は v1 では作らない（利用者がタスクスケジューラに登録する手順を示す）

### 2.2 二重起動の防止

- パイプを `FILE_FLAG_FIRST_PIPE_INSTANCE` で作る。失敗したら、既に動いているデーモンがあるとみなして終わる
- PID ファイル（`daemon\daemon.pid`）は参考の記録とし、判定には使わない（異常終了で残っても次の起動を妨げない。NFR-05）

### 2.3 終了

| きっかけ | 動き |
|---|---|
| アイドル（要求が無い）が `idle_timeout`（既定 2 時間）続いた | ブラウザを閉じて終わる |
| `llmc daemon stop`（`shutdown` 要求） | 実行中の要求があれば、その終わりを待つ（`--now` なら取り消す）。キューの要求は `Cancelled` で返す |
| ログオフ・シャットダウン | 受け取ったら、ブラウザを閉じて終わる（隠しウィンドウで `WM_QUERYENDSESSION` を受ける） |
| 異常 | 次の要求でクライアントが起動し直す |

- 終わるときに、ブラウザのプロファイルのロック（Edge の `lockfile` など）が残らないよう、ブラウザを正しく閉じる。残っていた場合は、次の起動で「プロファイルを使っているプロセスが無いこと」を確かめてから使う

## 3. プロセス間通信

### 3.1 パイプ

- 名前: `\\.\pipe\llmc-<利用者の SID>`
- DACL: `D:P(A;;FA;;;<本人の SID>)(A;;FA;;;SY)`（本人と SYSTEM だけ）。ctypes で作る（pywin32 は必須にしない）
- サーバは `FILE_FLAG_FIRST_PIPE_INSTANCE` で最初のインスタンスを作る
- クライアントは、つないだ後に `GetNamedPipeServerProcessId` でサーバのプロセスを調べ、その所有者の SID が自分であることを確かめる。違えば切る（乗っ取りへの対策）
- 認証キー: デーモンが起動ごとに 32 バイトの乱数を作り、`daemon\auth.key`（本人だけが読める）に書く。クライアントは最初のメッセージでそのキーの HMAC を送る（サーバが送る乱数に対して）。DACL と所有者の確認に加えた多重の対策

### 3.2 メッセージ

- 4 バイトの長さ（リトルエンディアン）＋ UTF-8 の JSON。1 メッセージの上限 16 MB（本文 60,000 文字と添付のパスで足りる。超えたら切断）
- 最初に `hello`（プロトコルの版、クライアントの版、認証）。版が合わなければ、デーモンは `version_mismatch` を返す。クライアントは、デーモンにほかの要求が無ければ止めて起動し直す
- 要求 1 件に対し、進捗のイベントが 0 件以上、最後に結果が 1 件。どれにも要求の `request_id` と実行 ID（NFR-13）を付ける

### 3.3 要求

| 要求 | 内容 | 結果 |
|---|---|---|
| `hello` | 版、認証 | デーモンの版、状態 |
| `health` | — | 状態（`starting` / `ready` / `login_required` / `browser_closed` / `rate_limited`）、サイトごとのログインの状態、キューの長さ、送信の数（時間・日）、プロファイルの版 |
| `turn` | サイト、会話の指定（新規・URL）、エージェント、本文（`OutboundMessage`）、添付（`daemon\staging\` のパス）、抽出の指定、タイムアウト、`max_wait_queue_s` | `TurnResult`（spec-browser-driver 2 章）か、エラー |
| `cancel` | `request_id` | 取り消したか |
| `login` | サイト | ウィンドウを元に戻し、ログインの画面を出す（spec-auth 4 章）。ログインできたら結果を返す |
| `conversations` | サイト | 会話の一覧（対応するサイトだけ） |
| `download` | サイト、会話、回答の中のファイル | `daemon\downloads\` のパス |
| `shutdown` | `now` | — |

- 進捗のイベントの名前と意味は spec-browser-driver 2.3 を正とする。キューで待つ間は `queued`（前に何件あるか）を送る

## 4. ブラウザの管理

### 4.1 起動と最小化

- サイトごとに 1 つの persistent context（`%LOCALAPPDATA%\llmc\profiles\<site>`）。起動するのは、そのサイトの最初の要求が来たとき
- 起動の後、DevTools プロトコルの `Browser.setWindowBounds` で最小化する（プロファイルの `browser.window: minimized`）
- 送信の前に、ウィンドウが最小化されていなくても**元に戻させない・前面に出さない**。利用者が開いて見ている場合は、そのまま操作する（利用者の操作と競合しうる。4.3）

### 4.2 ブラウザが閉じられた・落ちた

| 事象 | 検知 | 動き |
|---|---|---|
| 利用者がウィンドウを閉じた | context の `close`、browser の `disconnected` | 状態を `browser_closed` にする。次の `turn` で起動し直す。実行中の要求は `BrowserCrashed` で返す（再送しない。送ったかどうか分からないため） |
| ブラウザが落ちた | 同上、ページの `crash` | 1 回だけ起動し直す。実行中の要求は失敗として返す |
| Edge の更新による再起動 | 同上 | 同上（PoC-8 で確かめる） |

- 送ったかどうか分からない要求を自動で送り直さない。ループは、そのラウンドの状態を見て決める（spec-loop 10.3）

### 4.3 利用者の操作との競合

- 利用者が常駐のウィンドウを元に戻して操作している間に送信すると、入力が混ざる恐れがある
- v1: 送信の直前に、入力欄が空であることを確かめる（空でなければ `InputBusy` で返し、利用者に知らせる）。それ以外の検知はしない
- `llmc login` の間（spec-auth 4 章）は、キューを止める

## 5. キュー

- サイトごとに直列（1 度に 1 つの `turn`）。違うサイトの要求は並行してよい（v1 は 1 サイトしか使わない想定）
- 順は来た順。優先度は持たない
- キューの長さの上限は 20。超えたら `QueueFull` で返す
- `max_wait_queue_s`（既定 30 分）を超えて待った要求は `QueueTimeout` で返す
- 取り消し（FR-COM-11）
  - キューの中: 取り除いて `Cancelled` を返す
  - 送信の前: 送らずに `Cancelled`
  - 送信の後: 画面の停止ボタンを押し、`Cancelled`（回答の途中までは返さない）
- クライアントが切れた（Ctrl+C でクライアントが終わった、など）ら、その要求を取り消す

## 6. 並行の仕組み

- **ブラウザの操作は 1 つのスレッドに閉じ込め、Playwright の同期 API を使う**（PoC と同じ API。同期 API はスレッドをまたいで使えないため、ほかのスレッドから触らない）
- パイプの受け付けと各接続は別のスレッド。要求はスレッド間のキューでブラウザのスレッドへ渡す
- 取り消しは、要求ごとの旗を立てる。ブラウザのスレッドは、回答の待ちのループ（spec-browser-driver 6 章。500 ミリ秒ごとに状態を見る）で旗を見て、停止ボタンを押す
- 進捗のイベントは、ブラウザのスレッドが接続ごとの送信キューに入れる

## 7. 送信の数え上げ（NFR-14）

- サイトごとに、送信の時刻を `daemon\sends.jsonl` に追記する（再起動しても数えられるように。中身は時刻とサイトと実行 ID だけで、本文は書かない）
- 設定 `limits.sends_per_hour`・`limits.sends_per_day`（既定は無し。ループ側の `stop.max_sends_per_hour` は別に効く。spec-loop 11 章）。超えそうなら `turn` を待たせる（時間）か、`LocalLimit` で返す（日）
- 画面の上限の表示（`RateLimited(kind=daily)`）を受けたら、状態を `rate_limited` にし、表示から戻る時刻が分かればそれまで、分からなければ 1 時間、そのサイトの `turn` を即座に `RateLimited` で返す。`health` で解除の時刻を示す

## 8. ファイル

```
%LOCALAPPDATA%\llmc\daemon\
  auth.key        認証キー（起動ごとに作り直す。本人だけ）
  daemon.pid      参考の記録
  daemon.log      ログ（実行 ID ごと。本文は書かない。7 日で回す）
  sends.jsonl     送信の時刻
  staging\        添付用の一時ファイル（クライアントがマスキングして置く。送信の後に消す）
  downloads\      ダウンロードしたファイル（クライアントが移す。24 時間で消す）
```

- **ログに本文・回答・会話の題名を書かない**。長さ、ハッシュ、抽出の方式、所要時間、エラーの種類だけ（画面の会話の一覧には利用者の過去の会話の題名が出るため）
- 画面の不具合の報告（`diag\`、spec-browser-driver 10 章）のスクリーンショットには、会話の一覧と利用者の名前が写る。保存の前に会話の一覧の部分を塗りつぶす。共有する前に確かめるよう案内する

## 9. スリープ・画面のロック・RDP

- 送信と抽出が、画面のロック、RDP の切断、スリープの間も続くかは PoC-8 で確かめる
- 想定の扱い（PoC-8 で確定）
  - ロック・RDP の切断: 続けられれば何もしない。止まる場合は、`turn` の前に状態を確かめて `SessionLocked` で返す
  - スリープからの復帰: ブラウザの接続を確かめ、ページを読み直す。スリープを挟んだ要求は `Timeout` か `BrowserCrashed` として返す
  - ループの途中でのスリープを防ぐ（`SetThreadExecutionState(ES_SYSTEM_REQUIRED)`）かは、利用者の設定にする（既定は防がない）

## 10. 監視とログイン

- ログインの状態の判定・自動の再ログイン・`llmc login` は spec-auth
- デーモンは `turn` の前に、ページがログインの画面に転送されていないかを確かめる（spec-auth 3 章）

## 11. エラー

| エラー | 意味 | クライアントの扱い |
|---|---|---|
| `QueueFull` / `QueueTimeout` | キューの上限・待ちの上限 | 終了コード（spec-shell-integration） |
| `Cancelled` | 取り消した | 同上 |
| `InputBusy` | 入力欄に利用者の入力がある | 利用者に知らせる |
| `BrowserCrashed` | ブラウザが閉じられた・落ちた | ループは送ったかどうかを確かめて決める |
| `LoginRequired` | spec-auth | `llmc login` を案内 |
| `RateLimited` / `LocalLimit` | 7 章 | ループを止める（spec-loop 11 章） |
| `version_mismatch` | クライアントとデーモンの版が違う | デーモンを起動し直す |

## 12. PoC-8 で確かめること

| 項目 | 確かめること | 決めること |
|---|---|---|
| (a) 常駐 | pythonw から画面ありの Edge を起動して最小化し、クライアントの終了後も残るか。利用者がウィンドウを閉じた・元に戻したときの検知。Edge の更新による再起動 | 2.1・4.2・4.3 |
| (b) ロック・RDP・スリープ | 画面のロック、RDP の切断、スリープの間も送信と抽出が続くか | 9 章 |
| (c) スケジューラ | タスクスケジューラ（ジョブの中）からの起動で、デーモンがジョブの外に出られるか | 2.1 |
| (d) ログインの保持 | spec-auth 7 章 | spec-auth |
| (e) プロファイル | Playwright 用の別の user-data-dir がポリシーで拒否されないか | 4.1、spec-auth |
