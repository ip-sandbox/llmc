# 実行の形の仕様（v1: デーモンを作らない）

> **状態: 下書き**（2026-11-28）。v1 はデーモンを作らず、1 つのプロセスがブラウザを持つ形にした（plan 前提 19）。Opus のサブエージェントのレビューを受けて直した（Ctrl+C とドライバ、ロックの名前空間、起動用のプログラムとジョブ、コンソールを閉じたとき）。この形に固有の仕組み（ロック、ジョブ、Ctrl+C、タスクスケジューラ）と、画面のロック・スリープ、ウィンドウを閉じたときの検知は PoC-8 で確かめ、その結果で確定する（plan 5.6 の 6）。確かめる項目は 10 章にまとめた。前の版（デーモンの設計）は付録 A に残した。

## 1. 範囲と前提

- llmc のプロセスの形、起動の入口、同時に 1 つしか動かさない仕組み、ブラウザの持ち方、取り消し、送信の数え上げを定める
- 決めたこと（plan 前提 19・20）

| 項目 | 決定 | 理由 |
|---|---|---|
| デーモン | **v1 では作らない**。各コマンドのプロセスが、自分でブラウザを開いて使う | プロセス間通信（名前付きパイプの権限、認証キー、乗っ取りの対策、メッセージの形式）、キュー、ジョブからの切り離し、pythonw、自動の起動と終了がすべて要らなくなる |
| 同時に動く llmc | **1 つだけ**。2 つ目は起動の直後に断る（3 章） | 利用者は本人だけで、1 つのターミナルから使う。要求の順番待ち（キュー）が要らなくなる |
| 起動の入口 | `llmc` の 1 つ。引数なしで対話のセッション、サブコマンドで単発（2 章） | セッションの中ではブラウザを開いたままにできるので、起動の待ち（約 20 秒）は最初の 1 回で済む |
| RDP | 使わない（利用者、2026-11-28） | RDP の切断の間の動作は確かめない、扱わない |
| ブラウザ | 画面ありの Edge を最小化して使う。組織の PC ではヘッドレスがポリシーで禁止されている（`HeadlessModeEnabled=false`）。**回避しない** | plan 前提 2 |

- 引き換えに、できなくなること
  - 対話のセッションを開いている間に、別のターミナルから `git diff | llmc ask` を実行すること（断られる。セッションの中の `/ask -i`・`/run` で代わりにする。2.2）
  - セッションを開いている間の、タスクスケジューラからの実行（既定では断られる。`--wait-busy` で待てる。3.1）
  - ループを流しながら、別の画面で対話すること
  - 単発のコマンドは、毎回ブラウザの起動を待つ（PoC-8 の準備で、準備ができるまで 18.7 秒）
- 単発のコマンドの待ちが問題になったら、v2 でデーモンを足す（付録 A）。`ChatBackend`（spec-browser-driver 2 章）は、プロセスの中で使っても、デーモンの向こうで使っても同じ形なので、上の層は変わらない

## 2. 起動の入口

### 2.1 2 つの使い方

| 使い方 | ブラウザ | 向いている用途 |
|---|---|---|
| `llmc`（引数なし）: 対話のセッション（spec-tui） | 最初に送るときに開き、セッションが終わるまで開いたまま | 日中の作業。対話、`/ask`、`/convert`、`/loop` を続けて使う |
| `llmc ask ...`・`llmc convert ...`・`llmc loop ...` など: 単発 | 送るときに開き、コマンドの終わりに閉じる | パイプ、スクリプト、タスクスケジューラ（spec-shell-integration） |

- どちらも同じプログラム（venv の console script `llmc.exe`）で、同じプロセスの中で動く。セッションの中のコマンドは、単発のコマンドと同じ処理を呼ぶ（引数の形もそろえる）
- ブラウザは、**送信が要るときにはじめて開く**。送信の無い処理（レシピで固定したスクリプトの変換（spec-convert 9.2）、`llmc undo`、`llmc runs`、`--dry-run`）ではブラウザを開かない
- 人が送信する方式（spec-browser-driver 13 章）のサイトでは、ブラウザを開かない
- タスクスケジューラから使うときは、タスクを**「ユーザーがログオンしているときのみ実行する」**にする（必須。spec-shell-integration の手順に書く）。「ログオンしているかどうかにかかわらず」はセッション 0 で動き、画面ありの Edge が利用者に見えず、ログインもできないため

### 2.2 セッションの中で、シェルの出力を渡す

セッションを開いている間は、別のターミナルからのパイプが使えない（3 章で断られる）。代わりに、セッションの中で次を使う。

- `/ask -i <ファイル> <要求>`: ファイルを入力にする（`-i` は複数指定できる）
- `/run <コマンド> -- <要求>`: llmc がコマンドを実行し、その出力を入力にする（例: `/run git diff -- レビューして`）。コマンドは利用者が打ったものだけを実行する。出力にもマスキングをかける。実行の仕方は spec-loop 7 章の実行器と同じ（シェルを通すのは `/run !` で明示したときだけ）
- `/paste`: クリップボードのテキストを入力にする（表示する前に文字数だけ示す）

### 2.3 終わり方

| きっかけ | 動き |
|---|---|
| 単発のコマンドが終わった | ブラウザを閉じる（`context.close()`） |
| セッションを閉じた（`/quit`、Ctrl+D） | 同上 |
| ターミナルのウィンドウを × で閉じた・ログオフ | **閉じる処理は試みない**。Edge はジョブ（3.3）で終わる。コンソールの制御ハンドラは OS の別のスレッドで呼ばれ、約 5 秒で強制終了されるうえ、Playwright の同期 API は別のスレッドから呼べないため |
| 異常終了 | 同上。次の起動を妨げない（3.2） |

- Edge が強制終了されると、次の起動で「ページを復元しますか」の表示が出て、画面の操作を妨げることがある。起動の前にプロファイルの終了状態を「正常」に直す（`Default\Preferences` の `profile.exit_type`）。個人の PC で、強制終了の後に `exit_type` が `Crashed` になり、起動の前に `Normal` に直せることを確かめた。表示が実際に消えるかは、PoC-8 の (c) で画面を見て確かめる
- セッションでの放置（アイドル）でブラウザを閉じる機能は作らない（日中ずっと開いておく使い方のため）。`/browser close` で閉じ、次の送信で開き直す

## 3. 同時に 1 つだけ

### 3.1 断り方

- 起動したら、最初に `%LOCALAPPDATA%\llmc\state\llmc.lock` を開き、`LockFileEx`（排他、待たない）でロックする
  - プロセスが終われば（異常終了でも）OS がロックを外す。ロックのファイルが残っても、次の起動を妨げない（NFR-05）
  - ファイルのロックは、ログオンのセッションによらず効く。名前付きのミューテックスの `Local\` 名前空間はセッションごとに別なので、タスクスケジューラがセッション 0 で起動した llmc を断れない。そのためミューテックスは使わない
- ロックできなければ、すぐに「別の llmc が動いています（PID 1234、`llmc`（セッション）、10:12 から）」と stderr に出し、`EXIT_BUSY` で終わる。既定では待たない（待つと、パイプやスケジューラが黙って止まって見えるため）
  - `--wait-busy <秒>`: その秒数まで、ロックが外れるのを待つ（タスクスケジューラ向け。日中にセッションを開いている使い方では、スケジューラの実行はセッションを閉じた後の時刻にするよう案内する）
- 持ち主の情報（本当の Python の PID、コマンドの種類、開始の時刻）は、ロックしたファイルの中に書く。表示のためだけに使い、判定には使わない
- ロックを取らないコマンド: `--help`、`--version`、`llmc doctor`（読むだけの確かめ）、`llmc runs list`・`show`（読むだけ）。これらはセッションを開いたままでも、別のターミナルから使える
- ロックを取るコマンド: 上以外のすべて。書き込むもの（`llmc loop approve`・`llmc recipe approve`・`llmc runs prune`・`llmc logout`・`llmc undo` など）も含む

### 3.2 異常終了の後

- 書き込み中のジャーナル（spec-file-protocol 10.3）は、**毎回の起動で**ロックを取った後に確かめ、あれば戻してから続ける（前の llmc が異常終了したかを、ロックからは知れないため）
- Edge のプロファイルのロック: llmc が落ちても、Edge のプロセスが残っていると、同じプロファイルを開けない。3.3 のジョブでそれを防ぐ。それでもプロファイルを開けない場合（`ProfileInUse`。Playwright のどのエラーで分かるかは実装の初期に確かめる）は、残っている `msedge.exe` のうち、コマンドラインの `--user-data-dir` が llmc のプロファイルのものを示す。`llmc doctor --kill-stale` で終わらせられる（llmc 専用のプロファイルなので、利用者のふだんの Edge を巻き込まない）

### 3.3 Edge のプロセスの後始末

- **起動用のプログラムが 2 段ある**: console script の `llmc.exe`（pip の起動用プログラム）が venv の `python.exe` を起動し、venv の `python.exe`（起動用の小さなプログラム）が本当の Python を起動する。どちらの起動用のプログラムも、子を自分のジョブ（`KILL_ON_JOB_CLOSE`、子の子は黙って抜ける `SILENT_BREAKAWAY_OK` 付き。PoC-8 の準備で pythonw で同じ形を確認）に入れると見られる。そのため、本当の Python が起動するドライバ（node）と Edge は、起動用のプログラムのジョブには入らない
- そこで、本当の Python は起動の直後に**自分用のジョブ**を作って自分を入れ、`JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` を付ける（入れ子のジョブ。Windows 8 以降）。その後に起動するドライバと Edge がこのジョブに入り、llmc が落ちるとジョブが閉じて Edge も終わる
  - **個人の PC で確かめた**（PoC-8 の (c) の準備、2026-11-28）: pip と同じ形の起動用のプログラム（`llmc-poc8.exe`）から起動すると、`llmc-poc8.exe` はジョブの外、venv の `python.exe` と本当の Python はジョブの中だった（2 段の起動用のプログラムを確認）。本当の Python は自分用のジョブを作って入れた。その後に起動したドライバ（node 1 つ）と Edge（7 つ）は、すべて自分用のジョブに入った。`taskkill /F` で本当の Python を終わらせると、node と Edge は 1 つも残らなかった
  - **個人の PC で確かめた**（PoC-8 の (c)、2026-11-29、送信なし）: 起動 6 回のすべてで、2 つ目を断れ（rc=3）、自分用のジョブに入れた。`taskkill /F` とターミナルを × で閉じたときのどちらも、node と Edge は残らなかった。タスクスケジューラ（ログオンしているときのみ）の下では、`llmc-poc8.exe` もスケジューラのジョブに入っていたが、入れ子で自分用のジョブを作れ、Edge（7 つ）はすべてそこに入った
  - cmd.exe から起動した 2 回で、Edge でも node でもない子が 1 つ、自分用のジョブに入っていなかった（終わった後には残っていなかった）。名前を記録するようにしたので、次の実行で何かを確かめる
  - 組織の PC（ジョブの方針が違うことがある）では、PoC-8 の (c) で確かめる
- 自分をジョブに入れられなかった場合は、Edge を起動した後に、その PID（コマンドラインの `--user-data-dir` で見分ける）を `state\llmc.lock` に書いておく。次の起動で残っていれば、3.2 の案内を出す。`llmc doctor` で、Edge がジョブに入っているかを示す
- ユーザー定義のコマンドを入れるジョブ（spec-loop 7.4。`BREAKAWAY_OK` を付けない）は、この中にさらに入れ子で作る

## 4. ブラウザの管理

### 4.1 起動と最小化

- サイトごとの persistent context（`%LOCALAPPDATA%\llmc\profiles\<site>`）。v1 は 1 サイトだけを開く
- `launch_persistent_context` には、**`handle_sigint=False`・`handle_sigterm=False`・`handle_sighup=False` を必ず渡す**（既定の `True` では、Ctrl+C でブラウザが閉じられる。5 章）
- 起動の後、DevTools プロトコルの `Browser.setWindowBounds` で最小化する。最小化までの短い間、ウィンドウが見える。起動の引数（`--start-minimized` など）で見えなくできるかは PoC-8 で確かめる（Chromium の正式なスイッチではないので、効かなくても想定内）
- 送信の前に、ウィンドウを元に戻させない・前面に出さない。利用者が開いて見ている場合は、そのまま操作する

### 4.2 ブラウザが閉じられた・落ちた

| 事象 | 検知 | 動き |
|---|---|---|
| 利用者がウィンドウを閉じた | context の `close`、browser の `disconnected` | 送信中なら `BrowserCrashed`（送り直さない。送ったかどうか分からないため）。次の送信で開き直す |
| ブラウザが落ちた | 同上、ページの `crash` | 同上 |
| Edge の更新による再起動 | 同上 | 同上（PoC-8 で確かめる） |

- ループは、そのラウンドの状態を見て決める（spec-loop 10.3）

### 4.3 利用者の操作との競合

- 利用者が llmc のウィンドウを元に戻して操作している間に送信すると、入力が混ざる恐れがある
- 送信の直前に、入力欄が空であることを確かめる（空でなければ `InputBusy`）。それ以外の検知はしない
- llmc のプロファイルはふだんの Edge と別なので、利用者がふだんの Edge で Copilot を使うことは妨げない（plan 前提 9）

## 5. 並行の仕組みと取り消し

- プロセスは 1 つ、ブラウザの操作は主のスレッドで、Playwright の同期 API を使う（PoC と同じ）。スレッドは作らない
- 待ちは `time.sleep` ではなく `page.wait_for_timeout` で行う。同期 API では、`expose_binding`（生成中の文字の受け取り。spec-browser-driver 6.1）やイベントの処理は、Playwright の呼び出しの中でしか進まないため
- **Ctrl+C はコンソールにつながるすべてのプロセスに届く**。Playwright はドライバ（node）を、ウィンドウを隠すだけで同じコンソールのまま起動する（`playwright/_impl/transport.py` で確認）。そのため、何もしないと Ctrl+C でドライバが終わり、停止ボタンを押す前に Edge との接続が切れる
- 取り消し（FR-COM-11）の仕組み
  - 送信と回答の待ちの間は、コンソールの入力モードから `ENABLE_PROCESSED_INPUT` を外す（`CONIN$` を開いて `SetConsoleMode`。stdin がパイプでも効く）。Ctrl+C は OS のシグナルにならず、キーの入力（0x03）として届くので、待ちのループ（spec-browser-driver 6 章。500 ミリ秒ごとに状態を見る）がそれを読む
  - 読んだら、画面の停止ボタンを押し、`Cancelled` にする。送る前なら送らない
  - 待ちが終わったら、入力モードを元に戻す（例外で抜けても戻す）
  - コンソールが無い起動では、取り消しは無い（タイムアウトで終わる）。タスクスケジューラの「ログオンしているときのみ」では、コンソールのウィンドウが開き、Ctrl+C をキーとして読めた（個人の PC、PoC-8 の (c)）
- 生成中の表示（ストリーミング）は、同じ待ちのループの中で画面の文字を読んで出す。セッションでは、生成中の入力は Ctrl+C だけを受ける
- 待っている間（送信なし）に Ctrl+C を押すと、キーとして読め、ドライバと Edge は残って操作を続けられた（個人の PC で 2 回、PoC-8 の (c)、2026-11-29）
- 「生成中に Ctrl+C を押しても、ドライバと Edge が残り、停止ボタンを押せる」ことを PoC-8 の (c) で確かめる（送信が要る）

## 6. 送信の数え上げ（NFR-14）

- 送信の時刻を `state\sends.jsonl` に追記する（実行をまたいで数えるため。中身は時刻とサイトと実行 ID だけで、本文は書かない）。**送信のボタンを押す前に**追記する（押した直後に落ちても、数え漏れが無いように）。同時に動く llmc は 1 つなので、ファイルのロックは要らない
- 設定 `limits.sends_per_hour`・`limits.sends_per_day`（既定は無し。ループの `stop.max_sends_per_hour` は別に効く。spec-loop 11 章）。超えそうなら、時間の上限は待つ、日の上限は `LocalLimit` で止める
- 画面の 1 日の上限の表示（`RateLimited(kind=daily)`）を受けたら、`state\rate_limit.json` に、サイトと解除の見込みの時刻（表示から分かれば。例: 個人版の「午前 9:00」。分からなければ 1 時間後）を書く。その時刻までは、**ブラウザを開く前に** `EXIT_RATE_LIMITED` で止める（起動の 20 秒と送信を無駄にしない）。`--ignore-rate-limit` で確かめ直せる

## 7. ファイル

```
%LOCALAPPDATA%\llmc\
  state\
    llmc.lock         同時に 1 つだけにするロック。中身は持ち主の表示用の情報と、ジョブに入れられなかったときの Edge の PID（3 章）
    sends.jsonl       送信の時刻（6 章）
    rate_limit.json   1 日の上限の表示を受けた記録（6 章）
  logs\               ログ（実行 ID ごと。本文は書かない。7 日で回す）
  profiles\<site>\    ブラウザのプロファイル（spec-auth 8 章）
```

- 添付用の一時ファイル（マスキング済み）とダウンロードしたファイルは、その実行の run ディレクトリに置く（デーモンが無いので、受け渡しの専用の場所は要らない。spec-convert 10.1）
- **ログに本文・回答・会話の題名を書かない**。長さ、ハッシュ、抽出の方式、所要時間、エラーの種類だけ（画面の会話の一覧には利用者の過去の会話の題名が出るため）
- 画面の不具合の報告（`diag\`、spec-browser-driver 10 章）のスクリーンショットには、会話の一覧と利用者の名前が写る。保存の前に会話の一覧の部分を塗りつぶす。共有する前に確かめるよう案内する

## 8. スリープ・画面のロック

- RDP では使わない（1 章）。RDP の切断は扱わない
- 送信と抽出が、画面のロックとスリープの間も続くかは PoC-8 で確かめる
- 想定の扱い（PoC-8 で確定）
  - 画面のロック: 続けられれば何もしない。止まる場合は、送信の前に状態を確かめて `SessionLocked` で止める
  - スリープからの復帰: ブラウザの接続を確かめ、ページを読み直す。スリープを挟んだ送信は `Timeout` か `BrowserCrashed` にする
  - ループの途中でスリープを防ぐ（`SetThreadExecutionState(ES_SYSTEM_REQUIRED)`）かは、利用者の設定にする（既定は防がない）

## 9. エラー

| エラー | 意味 | 扱い |
|---|---|---|
| `Busy` | 別の llmc が動いている（3 章） | `EXIT_BUSY`（番号は spec-shell-integration） |
| `ProfileInUse` | プロファイルを残った Edge が使っている（3.2） | 案内して止める（`llmc doctor --kill-stale`） |
| `Cancelled` | 取り消した | 終了コード（spec-shell-integration） |
| `InputBusy` | 入力欄に利用者の入力がある | 利用者に知らせる |
| `BrowserCrashed` | ブラウザが閉じられた・落ちた | ループは送ったかどうかを確かめて決める |
| `LoginRequired` | spec-auth | `llmc login` を案内 |
| `RateLimited` / `LocalLimit` | 6 章 | 止める（spec-loop 11 章） |
| `SessionLocked` | 画面のロックの間は送れない（8 章。PoC-8 の結果しだい） | 止める |

## 10. PoC-8 で確かめること（v1 の形に合わせた）

| 項目 | 確かめること | 決めること |
|---|---|---|
| (a) ウィンドウ | 利用者がウィンドウを閉じた・元に戻したときの検知。Edge の更新による再起動。起動の引数で最初から最小化できるか | 4.1・4.2 |
| (b) ロック・スリープ | 画面のロックとスリープの間も、送信と抽出が続くか（RDP は確かめない） | 8 章 |

- (a)(b) は、PoC-8 の準備で作った `poc8_daemon\ctl.py` と `resident.py` で確かめられる（別のプロセスでブラウザを持つ形だが、ウィンドウとロックには関係しない）。(c) は v1 の形そのものなので、別のスクリプトで確かめる
- やめた項目: pythonw の下での常駐、ターミナルを閉じた後もブラウザが残るか、ジョブからの切り離し（どれもデーモンのための確認だった）、RDP の切断

## 11. 未決事項

- 単発のコマンドが多くなり、起動の待ちが問題になったら、v2 でデーモンを足す（付録 A）
- 複数のサイトを同時に開くか（v1 は 1 サイト）
- セッションで、2 つ目の llmc を断る代わりに、セッションへ要求を渡せるようにするか（それにはプロセス間の通信が要り、付録 A の一部を作ることになる）

## 付録 A. デーモンの案（v2 の候補。前の版の要点）
