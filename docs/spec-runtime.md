# 実行の形の仕様（v1: デーモンを作らない）

> **状態: 下書き**（2026-11-28）。v1 はデーモンを作らず、1 つのプロセスがブラウザを持つ形にした（plan 前提 19）。画面のロックとスリープの間の振る舞い、ウィンドウを閉じたときの検知は PoC-8 で確かめ、その結果で確定する（plan 5.6 の 6）。確かめる項目は 10 章にまとめた。前の版（デーモンの設計）は付録 A に残した。

## 1. 範囲と前提

- llmc のプロセスの形、起動の入口、同時に 1 つしか動かさない仕組み、ブラウザの持ち方、送信の数え上げを定める
- 決めたこと（plan 前提 19・20）

| 項目 | 決定 | 理由 |
|---|---|---|
| デーモン | **v1 では作らない**。各コマンドのプロセスが、自分でブラウザを開いて使う | プロセス間通信（名前付きパイプの権限、認証キー、乗っ取りの対策、メッセージの形式）、キュー、ジョブからの切り離し、pythonw、自動の起動と終了がすべて要らなくなる |
| 同時に動く llmc | **1 つだけ**。2 つ目は起動の直後に断る（3 章） | 利用者は本人だけで、1 つのターミナルから使う。要求の順番待ち（キュー）が要らなくなる |
| 起動の入口 | `llmc` の 1 つ。引数なしで対話のセッション、サブコマンドで単発（2 章） | セッションの中ではブラウザを開いたままにできるので、起動の待ち（約 20 秒）は最初の 1 回で済む |
| RDP | 使わない（利用者、2026-11-28） | RDP の切断の間の動作は確かめない、扱わない |
| ブラウザ | 画面ありの Edge を最小化して使う。組織の PC ではヘッドレスがポリシーで禁止されている（`HeadlessModeEnabled=false`）。**回避しない** | plan 前提 2 |

- 引き換えに、できなくなること
  - 対話のセッションを開いている間に、別のターミナルから `git diff | llmc ask` を実行すること（断られる。セッションの中の `/ask -i`・`/run` で代わりにする。2.2）
  - セッションを開いている間の、タスクスケジューラからの実行（断られる。`EXIT_BUSY`）
  - ループを流しながら、別の画面で対話すること
  - 単発のコマンドは、毎回ブラウザの起動を待つ（PoC-8 の準備で、準備ができるまで 18.7 秒）
- 単発のコマンドの待ちが問題になったら、v2 でデーモンを足す（付録 A）。`ChatBackend`（spec-browser-driver 2 章）は、プロセスの中で使っても、デーモンの向こうで使っても同じ形なので、上の層は変わらない

## 2. 起動の入口

### 2.1 2 つの使い方

| 使い方 | ブラウザ | 向いている用途 |
|---|---|---|
| `llmc`（引数なし）: 対話のセッション（spec-tui） | 最初に送るときに開き、セッションが終わるまで開いたまま | 日中の作業。対話、`/ask`、`/convert`、`/loop` を続けて使う |
| `llmc ask ...`・`llmc convert ...`・`llmc loop ...` など: 単発 | 送るときに開き、コマンドの終わりに閉じる | パイプ、スクリプト、タスクスケジューラ（spec-shell-integration） |

- どちらも同じプログラム（venv の console script `llmc.exe`）で、同じプロセスの中で動く。セッションの中のコマンドは、単発のコマンドと同じ処理を呼ぶ（引数の形もそろえる）
- ブラウザは、**送信が要るときにはじめて開く**。送信の無い処理（レシピで固定したスクリプトの変換（spec-convert 9.2）、`llmc undo`、`llmc runs`、`--dry-run`）ではブラウザを開かない
- 人が送信する方式（spec-browser-driver 13 章）のサイトでは、ブラウザを開かない

### 2.2 セッションの中で、シェルの出力を渡す

セッションを開いている間は、別のターミナルからのパイプが使えない（3 章で断られる）。代わりに、セッションの中で次を使う。

- `/ask -i <ファイル> <要求>`: ファイルを入力にする（`-i` は複数指定できる）
- `/run <コマンド> -- <要求>`: llmc がコマンドを実行し、その出力を入力にする（例: `/run git diff -- レビューして`）。コマンドは利用者が打ったものだけを実行する。出力にもマスキングをかける。実行の仕方は spec-loop 7 章の実行器と同じ（シェルを通すのは `/run !` で明示したときだけ）
- `/paste`: クリップボードのテキストを入力にする（表示する前に文字数だけ示す）

### 2.3 終わり方

| きっかけ | 動き |
|---|---|
| 単発のコマンドが終わった | ブラウザを閉じる |
| セッションを閉じた（`/quit`、Ctrl+D、ウィンドウを閉じた） | ブラウザを閉じる |
| ターミナルのウィンドウを閉じた・ログオフ | コンソールの閉じる通知（`CTRL_CLOSE_EVENT` など）を受けたら、ブラウザを閉じる。間に合わなくても、Edge のプロセスはジョブ（3.3）で終わる |
| 異常終了 | 同上。次の起動を妨げない（3.2） |

- セッションでの放置（アイドル）でブラウザを閉じる機能は作らない（日中ずっと開いておく使い方のため）。`/browser close` で閉じ、次の送信で開き直す

## 3. 同時に 1 つだけ

### 3.1 断り方

- 起動したら、最初に名前付きのミューテックス `Local\llmc-<利用者の SID>` を取る（`CreateMutexW`。ctypes）
- 取れなければ、すぐに「別の llmc が動いています（PID 1234、`llmc`（セッション）、10:12 から）」と stderr に出し、`EXIT_BUSY` で終わる。待たない（待つと、パイプやスケジューラが黙って止まって見えるため）
- 持ち主の情報（PID、コマンドの種類、開始の時刻）は `state\owner.json` に書く。表示のためだけに使い、判定には使わない
- ミューテックスを取らないコマンド: `--help`、`--version`、`llmc doctor`（読むだけの確かめ）、`llmc runs list`・`show`（読むだけ）。これらはセッションを開いたままでも、別のターミナルから使える

### 3.2 異常終了の後

- ミューテックスは、プロセスが終わると OS が手放す（異常終了なら「放棄された」状態になり、次の起動で取れる）。ロックのファイルが残って次の実行を妨げる問題が起きない（NFR-05）
- 次に取ったときに「放棄された」と分かったら、書き込み中のジャーナル（spec-file-protocol 10.3）を確かめてから続ける
- Edge のプロファイルのロック: llmc が落ちても、Edge の子のプロセスが残っていると、同じプロファイルを開けない。3.3 のジョブでそれを防ぐ。それでもプロファイルを開けない場合は、「このプロファイルを使っている Edge が残っています」と示して止める（自動では終わらせない。利用者がふだんの Edge で同じフォルダを開いた可能性があるため）

### 3.3 Edge のプロセスの後始末

- llmc は、起動の直後に自分をジョブオブジェクトに入れ、`JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` を付ける。Playwright が起動するドライバと Edge は、このジョブに入る。llmc が落ちると、ジョブが閉じて Edge も終わる
- llmc が既にジョブの中にいる場合（タスクスケジューラなど）は、入れ子のジョブになる（Windows 8 以降は使える）。入れられなかった場合は、警告を出して続ける
- ユーザー定義のコマンドを入れるジョブ（spec-loop 7.4）は、この中に別に作る

## 4. ブラウザの管理

### 4.1 起動と最小化

- サイトごとの persistent context（`%LOCALAPPDATA%\llmc\profiles\<site>`）。v1 は 1 サイトだけを開く
- 起動の後、DevTools プロトコルの `Browser.setWindowBounds` で最小化する。最小化までの短い間、ウィンドウが見える。起動の引数（`--start-minimized` など）で見えなくできるかは PoC-8 で確かめる
- 送信の前に、ウィンドウを元に戻させない・前面に出さない。利用者が開いて見ている場合は、そのまま操作する

### 4.2 ブラウザが閉じられた・落ちた

| 事象 | 検知 | 動き |
|---|---|---|
| 利用者がウィンドウを閉じた | context の `close`、browser の `disconnected` | 送信中なら `BrowserCrashed`（送り直さない。送ったかどうか分からないため）。次の送信で開き直す |
| ブラウザが落ちた | 同上、ページの `crash` | 同上 |
| Edge の更新による再起動 | 同上 | 同上（PoC-8 で確かめる） |

- ループは、そのラウンドの状態を見て決める（spec-loop 10.3）

### 4.3 利用者の操作との競合

- 利用者が llmc のウィンドウを元に戻して操作している間に送信すると、入力が混ざる恐れがある
- 送信の直前に、入力欄が空であることを確かめる（空でなければ `InputBusy`）。それ以外の検知はしない
- llmc のプロファイルはふだんの Edge と別なので、利用者がふだんの Edge で Copilot を使うことは妨げない（plan 前提 9）

## 5. 並行の仕組み

- プロセスは 1 つ、ブラウザの操作は主のスレッドで、Playwright の同期 API を使う（PoC と同じ）。スレッドは作らない
- 取り消し（FR-COM-11）: Ctrl+C（`SIGINT`）で旗を立てる。回答の待ちのループ（spec-browser-driver 6 章。500 ミリ秒ごとに状態を見る）が旗を見て、画面の停止ボタンを押し、`Cancelled` にする。送る前なら送らない
- 生成中の表示（ストリーミング）は、同じ待ちのループの中で画面の文字を読んで出す。セッションでは、生成中の入力は Ctrl+C だけを受ける

## 6. 送信の数え上げ（NFR-14）

- 送信の時刻を `state\sends.jsonl` に追記する（実行をまたいで数えるため。中身は時刻とサイトと実行 ID だけで、本文は書かない）。同時に動く llmc は 1 つなので、ファイルのロックは要らない
- 設定 `limits.sends_per_hour`・`limits.sends_per_day`（既定は無し。ループの `stop.max_sends_per_hour` は別に効く。spec-loop 11 章）。超えそうなら、時間の上限は待つ、日の上限は `LocalLimit` で止める
- 画面の 1 日の上限の表示（`RateLimited(kind=daily)`）を受けたら、`state\rate_limit.json` に、サイトと解除の見込みの時刻（表示から分かれば。例: 個人版の「午前 9:00」。分からなければ 1 時間後）を書く。その時刻までは、**ブラウザを開く前に** `EXIT_RATE_LIMITED` で止める（起動の 20 秒と送信を無駄にしない）。`--ignore-rate-limit` で確かめ直せる

## 7. ファイル

```
%LOCALAPPDATA%\llmc\
  state\
    owner.json        いま動いている llmc（表示のためだけ。3.1）
    sends.jsonl       送信の時刻（6 章）
    rate_limit.json   1 日の上限の表示を受けた記録（6 章）
  logs\               ログ（実行 ID ごと。本文は書かない。7 日で回す）
  profiles\<site>\    ブラウザのプロファイル（spec-auth 8 章）
```

- 添付用の一時ファイル（マスキング済み）とダウンロードしたファイルは、その実行の run ディレクトリに置く（デーモンが無いので、受け渡しの専用の場所は要らない。spec-convert 10.1）
- **ログに本文・回答・会話の題名を書かない**。長さ、ハッシュ、抽出の方式、所要時間、エラーの種類だけ（画面の会話の一覧には利用者の過去の会話の題名が出るため）
- 画面の不具合の報告（`diag\`、spec-browser-driver 10 章）のスクリーンショットには、会話の一覧と利用者の名前が写る。保存の前に会話の一覧の部分を塗りつぶす。共有する前に確かめるよう案内する

## 8. スリープ・画面のロック

- RDP では使わない（1 章）。RDP の切断は扱わない
- 送信と抽出が、画面のロックとスリープの間も続くかは PoC-8 で確かめる
- 想定の扱い（PoC-8 で確定）
  - 画面のロック: 続けられれば何もしない。止まる場合は、送信の前に状態を確かめて `SessionLocked` で止める
  - スリープからの復帰: ブラウザの接続を確かめ、ページを読み直す。スリープを挟んだ送信は `Timeout` か `BrowserCrashed` にする
  - ループの途中でスリープを防ぐ（`SetThreadExecutionState(ES_SYSTEM_REQUIRED)`）かは、利用者の設定にする（既定は防がない）

## 9. エラー

| エラー | 意味 | 扱い |
|---|---|---|
| `Busy` | 別の llmc が動いている（3 章） | `EXIT_BUSY`（番号は spec-shell-integration） |
| `ProfileInUse` | プロファイルを他の Edge が使っている（3.2） | 利用者に知らせて止める |
| `Cancelled` | 取り消した | 終了コード（spec-shell-integration） |
| `InputBusy` | 入力欄に利用者の入力がある | 利用者に知らせる |
| `BrowserCrashed` | ブラウザが閉じられた・落ちた | ループは送ったかどうかを確かめて決める |
| `LoginRequired` | spec-auth | `llmc login` を案内 |
| `RateLimited` / `LocalLimit` | 6 章 | 止める（spec-loop 11 章） |
| `SessionLocked` | 画面のロックの間は送れない（8 章。PoC-8 の結果しだい） | 止める |

## 10. PoC-8 で確かめること（v1 の形に合わせて絞った）

| 項目 | 確かめること | 決めること |
|---|---|---|
| (a) ウィンドウ | 利用者がウィンドウを閉じた・元に戻したときの検知。Edge の更新による再起動。起動の引数で最初から最小化できるか | 4.1・4.2 |
| (b) ロック・スリープ | 画面のロックとスリープの間も、送信と抽出が続くか（RDP は確かめない） | 8 章 |
| (d) 朝のログインの画面 | spec-auth 7 章 | spec-auth |

- PoC-8 の準備で作った `poc8_daemon\ctl.py` と `resident.py` は、別のプロセスでブラウザを持つ形だが、(a)(b) の確かめには そのまま使える
- やめた項目: pythonw の下での常駐、ターミナルを閉じた後も残るか、ジョブからの切り離し、タスクスケジューラからの起動（どれもデーモンのための確認だった）、RDP の切断
- (e) Playwright 用の別のプロファイルがポリシーで拒否されないか: PoC-1b・PoC-3 の組織版で、別のプロファイルのまま使えたので済みとする

## 11. 未決事項

- 単発のコマンドが多くなり、起動の待ちが問題になったら、v2 でデーモンを足す（付録 A）
- 複数のサイトを同時に開くか（v1 は 1 サイト）
- セッションで、2 つ目の llmc を断る代わりに、セッションへ要求を渡せるようにするか（それにはプロセス間の通信が要り、付録 A の一部を作ることになる）

## 付録 A. デーモンの案（v2 の候補。前の版の要点）

v1 では作らない。単発のコマンドの起動の待ちが問題になったときに、この案から作る。

| 部分 | 案 | PoC の結果 |
|---|---|---|
| 起動 | クライアントがパイプにつなげなければ `pythonw.exe -m llmc.daemon` を `DETACHED_PROCESS \| CREATE_NEW_PROCESS_GROUP \| CREATE_BREAKAWAY_FROM_JOB` で起動する。アイドル 2 時間で終わる | pythonw の下で Playwright が動いた（H-13）。切り離しを許さないジョブの中からは、エラーにならずにジョブの中に残った。**venv の `pythonw.exe` は起動用の小さなプログラム**で、本当の Python はその子になり、起動用のプログラムのジョブに入る（PoC-8 の準備）。ジョブの外に出られたかは、起動用のプログラムの側で確かめる |
| 二重起動 | パイプを `FILE_FLAG_FIRST_PIPE_INSTANCE` で作る。PID ファイルは参考だけ | 同じ名前のパイプが既にあれば作れなかった（PoC-4） |
| パイプ | `\\.\pipe\llmc-<SID>`。DACL `D:P(A;;FA;;;<本人の SID>)(A;;FA;;;SY)`。クライアントは `GetNamedPipeServerProcessId` でサーバの所有者を確かめる。起動ごとの認証キー（`auth.key`）の HMAC | 標準ライブラリのパイプは Everyone と匿名に読み取りを許す。ctypes で本人と SYSTEM だけにできた（H-12） |
| メッセージ | 4 バイトの長さ＋ UTF-8 の JSON（上限 16 MB）。`hello`・`health`・`turn`・`cancel`・`login`・`conversations`・`download`・`shutdown` | — |
| キュー | サイトごとに直列。上限 20 件、待ちの上限 30 分。取り消しはキューの中・送信の前・送信の後で分ける | — |
| 並行 | ブラウザの操作を 1 つのスレッドに閉じ込め、同期 API を使う。パイプの接続は別のスレッド | — |
| 置き場所 | `%LOCALAPPDATA%\llmc\daemon\`（`auth.key`、`daemon.log`、`sends.jsonl`、添付の `staging\`、`downloads\`） | — |

- デーモンを足しても、本書の 4 章（ブラウザの管理）・6 章（数え上げ）・7 章（ログの方針）・8 章はそのまま使える。変わるのは、プロセスの形（2・3・5 章）だけ
