# llmc 設計作業計画（初版）

- 対象: llmc（社内 AI チャット用ターミナルクライアント、Python 製、Windows 専用）
- 本書の位置づけ: 設計書・仕様書（`docs/` 配下 17 成果物）を作成するための作業計画と、着手前に確定した前提の記録
- 参考実装（cploop.py / cpagent.py）とキックオフ資料そのものはリポジトリに登録しない。必要な箇所は各設計書で要約・引用する

## 2. 参考実装レビューの要旨

詳細は `review-reference-impl.md`。キックオフ資料の問題点 13 件はすべてコードで確認した。さらに、次の追加指摘がある（抜粋）。

- 続きの依頼を上限まで使っても切れたままの回答を適用してしまう
- 自分のメッセージを回答として取り出すと、元の内容を書き戻しただけで「成功」に見える
- `conftest.py` や `pytest.ini` を AI が書くことで、変更禁止をすり抜けてテストを無効化できる
- Playwright のタイムアウトが捕まえられず、終了コード 1（最大ラウンド到達）と区別できない
- パイプ出力時に cp932 で `✅` を出力しようとして異常終了する
- テスト実行にタイムアウトが無い、undo が AI の新規ファイルを消さない、など

## 3. 設計上の主要論点（各仕様書で比較・確定する）

1. **ファイル書式**: メタ情報はすべてコードブロックの内側の行に置き、info 文字列は使わない（DOM 復元で失われるため）。フェンスは可変長にする。ファイルごとの完全性は、行数の申告ではなく、**ターンごとの ID を含む終了行をフェンスの内側に置く**方式とする。提案全体の完全性は、回答の冒頭の計画（項目の一覧）で確かめる（spec-file-protocol で確定）
2. **回答の特定**: DOM 上の発言者の属性を主に使い、nonce の書き返しを補助にする（自分のメッセージにも nonce が含まれるため、nonce だけでは判別できない）
3. **抽出**: コピーボタン（生の Markdown）を第一候補、DOM からの復元を次善の策とする。DOM 復元の場合は、ファイルごとの終了行が無いブロックを書き込まない
4. **ロールバック**: git に依存せず、run ディレクトリに元のバイト列を保存して戻すことを基本にする。git 連携は worktree を使う任意の機能にする
5. **実行器**: ループのコマンドはシェルを介さず引数リストで直接起動するのを既定とし、タイムアウトとプロセスツリーの強制終了を必須にする
6. **IPC**: 現在のユーザーだけに ACL を絞った名前付きパイプを第一候補にする
7. **シェル**: PowerShell 5.1 と cmd.exe の文字コードの扱いを比較して決める（1 章の 4）
8. **非対話モードと確認の衝突**: 1 章の 5 のとおり

## 5. 作業の進め方（PoC を挟む）

### 5.1 方針

- 書いた設計書（requirements、architecture、spec-file-protocol、spec-browser-driver、spec-agent）は**暫定版**とする。実物で確かめる仮説を 5.2 にまとめ、PoC の結果で確定・修正する
- PoC は `poc/` に置く使い捨てのプログラム。本体の設計や品質の基準は適用しない
- 分担: PoC を書き、模擬ページなどで動くところまで確かめるのは Claude。実機（Windows の PC と Copilot）での実行は利用者。結果のレポートをチャットに貼ってもらい、Claude が設計書に反映する
- 後続の仕様書は、関係する PoC の結果が出てから書く

### 5.4 注意

- 個人のアカウントの Copilot には、**社内の情報を送らない**。PoC の依頼文は、すべて架空の内容にする
- レポートは、貼る前に利用者が内容を確認できる Markdown で出す。環境変数から得た利用者名・PC 名・ホームのパスなどは、出力の前に置き換える

### 5.5 運用

- 段階ごとにコミットし、作業ブランチに push する。PR は指示があるまで作らない
- 設計の途中で判断に必要な情報が足りなければ、推測で埋めずに質問する
- 実画面で確かめるまで決められない事項は、仮の値を置いたうえで 5.2 の仮説か `open-questions.md` に必ず載せる
